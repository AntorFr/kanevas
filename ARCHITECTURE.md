# Architecture — kanevas

RPG management system (lore, campaigns, session reports, permissions, maps). What it enables,
for whom and through which screens: `docs/parcours.md`, `docs/ecrans.md`; its data: `docs/donnees.md`.

This document has two parts: **today**, the map of the code as it stands; **the target**,
the architecture of the whole product, set by the epic's scope and implemented slice by
slice (on `main`, the target describes only what has been built).

# Today

Since `kanevas-premiere-fiche`, the foundation (one Fastify application, Node 20, TypeScript,
`GET /healthz`, an OIDC mechanism, an image published by CI) carries the **first business
function**: accounts, universes, members, sheets and sections, with their permissions; sessions
and stub mode; the React frontend that displays them (home, universes, members, lore, sheet).
It also includes the game system and, with `kanevas-suivi`, session tracking: campaigns, scenarios,
preparation, session reports; `kanevas-relier-chercher`, relations between sheets and search (within a type, then across all types since `kanevas-import-recherche`; FTS5 indexes, AD-63, AD-64, AD-118); attachments (storage on the volume, E-9 block);
`kanevas-assistant-membre`, each member's assistant: a conversation panel whose tools
call the same service functions as the routes, with the person's permissions (AD-73 to AD-78).
Maps and graphs (E-10, E-11) are built. `kanevas-monde` adds a proposed section update based on a session report, which the GM applies or abandons with one action (AD-79 to AD-82); `kanevas-images` adds generation of a portrait attached to a section (AD-88 to AD-90).
`kanevas-recours-admin` adds instance administration (E-5, AD-86, AD-87).
`kanevas-outils-cadre` adds the tools framework (`src/outils/`, `services/outils.ts`, `routes/outils.ts`, migration `0017-outils.sql`, routes `/api/univers/:id/outils…` and `/api/systemes/:id/{outils,responsable}…`, tab « Outils » of E-14/E-15, sidebar section « Outils »): detail and decisions C-1 to C-6 in « Detail of `kanevas-outils-cadre` »; no real tool yet, only the trial module `essai` in stub mode and in test.
`kanevas-outils-galaxie-lire` adds the first real tool, the read side of the galaxy map (module `swn`, tool `galaxie`, migration `0018-swn-galaxie.sql` with provisional number, `src/outils/swn/`, `src/services/swn/`, screen E-21 in `frontend/src/outils/swn/galaxie/`, assistant tool `swn_galaxie_trajet`): detail and decisions G-1 to G-9 in « Detail of `kanevas-outils-galaxie-lire` »; like `essai`, the module registers only in stub mode and in test until a deployment lists it. Writing the map (place, route, zone, seed, import) is `kanevas-outils-galaxie-tenir`.

## Routes `/api`

The tools framework's routes (`/api/univers/:id/outils…`, `/api/systemes/:id/outils…`, `/api/systemes/:id/responsable…`) are tabulated in « Detail of `kanevas-outils-cadre` », C-5.

All guarded by the session (401 without a session), except `/api/auth/*` and `/api/import/v1/*`, which opens only with a Bearer token (AD-103) and ignores the cookie. Service errors are
`introuvable` 404, `refuse` 403, `invalide` 400, `conflit` 409 (`section_modifiee`, `nom_pris`, `gabarit_modifie`, `scenario_modifie`, `proposition_appliquee`, `relation_existante`, `limite_relations`, `limite_pieces`: 100 attached files per section (AD-111) — 409 for a GM, 403 `refuse` for another member (AD-117), `fiche_deja_placee` and `carte_pleine` for maps; 413 `fond_trop_lourd` for a background over 25 MB; 400 `fichier_vide` for an empty attachment (an empty map background is a 400 `fond_invalide`); `auto_relation` is a 400 `invalide`). Removing the last
GM returns `invalide` 400 with the reason; so does section content over 100,000 characters (AD-91). A service error body is `{message}` (plus `code` when the service supplies one); an `/api/...` address with no matching route (for example a route removed by AD-94) returns 404 with the « Page introuvable. » HTML page, rather than JSON. The server listens on `0.0.0.0` (`-p 3001:3001` suffices).
In stub mode, `POST /connexion-bouchon` expects a form-urlencoded body `compte=<identifiant>`.
The rows citing AD-93 or AD-94 belong to `kanevas-illustrations`, built by that slice;
they replace the old `GET /api/univers/:id/systeme` and `…/systeme/gabarits*` routes.

## Invariants

- **The version has a single source**: the Docker build-arg `APP_VERSION`, derived
  by CI from the pushed semver tag (outside a tag, the value is not a semver: only an image built
  from a tag carries one). `/healthz` and the published image tag therefore
  cannot diverge. `package.json` deliberately has no
  `version`.
- **`/healthz` is public** (alongside `/api/auth/*` and login pages, AD-15), as plain text `kanevas <version>`, without data.
  `GET /api/auth/config` (`{oidcEnabled}`) is public too; no other public
  route exposes content.
- **The OIDC callback authenticates an identity, nothing more**: it opens a session carrying
  the identifier and groups, and creates the account; **no universe role comes from Authelia**
  (AD-9), it is read from the members table on every request. Without the four
  `OIDC_*` variables (or with only some of them), login and callback return 404; an empty
  or invalid value causes startup to fail.
- **Twenty-six tables and two search indexes, no ORM**: `comptes`, `univers`, `membres`, `fiches`, `sections` (migration
  0001), `systemes_jeu`, `gabarits` (migration 0002), `campagnes`, `scenarios`, `taches_preparation` (migration 0003), `pieces_jointes` (migration 0004, emptied by 0015 and no longer read), `relations`, `recherche_fiches` and `recherche_sections` (FTS5, migration 0005); three illustration columns on `fiches` (migration 0006), `cartes` and `elements_carte` (migration 0007), `propositions` (migration 0008, `kanevas-monde`); `jetons_api` and `lots_import`, plus source keys on `fiches` and `sections` (migration 0010, `kanevas-import-fil`); `sections.contenu_public` and the rebuilt `recherche_sections` index (migration 0011, `kanevas-import-secrets`, AD-114); `liens` (migration 0012, `kanevas-import-liens`, AD-116); `types_systeme` and `types_univers`, and `fiches` rebuilt without a type `CHECK` (migration 0013, `kanevas-import-types`, AD-120); `fiche_alias`, `etiquettes` and `fiche_etiquettes`, and `recherche_fiches` rebuilt as `(titre, alias, sous_type)` (migration 0014, `kanevas-import-recherche`, AD-118); `fichiers`, `fichiers_sections` and `fiches.illustration_fichier_id` (migration 0015, `kanevas-import-mediatheque`, AD-117; `fichiers_attente`, created by the same migration, written by `assurerFichier` and sheet imports, `kanevas-import-fichiers`; the AD-93 illustration columns remain, unused); migration 0009 (`kanevas-import-markdown`) rebuilds `gabarits`, `scenarios` and `propositions` to raise their CHECK to 100,000 characters; numbers 0001 to 0007 are final, 0008 to 0016 are provisional until the epic merges into `main` and subsequent numbers are assigned at merge time (AD-51; `docs/donnees.md`). - **New repository, selective reuse from Antre-du-maitre (AD-10)**: Fastify
  bootstrap, OIDC, LLM transports, Dockerfile pattern and CI, without Prisma or the
  business domain. Rejected: forking Antre-du-maitre.

  is reused in the foundation. `claude-token.ts` (admin setup-token window) was not reused in the
  foundation; it is reused by `kanevas-import-jeton-assistant` (AD-109, AD-112).
- **No canary page**: the frontend starts with the first business page (AD-57).
- **Public repository, MIT licence**: the public GHCR package avoids a pull-secret and
  Renovate auto-bump; MIT in the absence of a shared licence policy across the fleet.
  Reversed only if the code must become confidential.
- **Version read from `package.json`**: rejected, two unsynchronised sources.
- In the cluster (`tantive`; Authelia is on `homenode`) the pod runs as `runAsUser: 0` (the `games` apps' convention for
  a writable hostPath): the image's `node` user (uid 1000) is
  tolerated, not required. Under uid 1000 it would need a hostPath writable by that user.

## Components, and who talks to whom

```
browser (React, one SPA)  ──HTTP──▶  Fastify backend (one application)
                                         ├─ HTTP routes ─┐
                                         ├─ agent tools (GM | Player) ─┤─▶ service functions ─▶ SQLite + /data/attachments
                                         ├─ LLM provider (assistant)
                                         └─ codex exec (images), as a subprocess
Authelia (OIDC): identity only.

import script (outside the product, on Monsieur's Mac)
      ──HTTPS, Bearer──▶  /api/import/v1/univers/:id  (separate scope: token, never a cookie)
                                         └─▶ the same service functions (AD-2, AD-104)
```

- **Browser**: one React application (`react-router`, AD-16), served by the backend; it
  talks only to the backend, never to the database or disk. The assistant thread lives in the page
  (AD-28).
- **Fastify backend**: the only access point to data, disk, the LLM provider and
  Codex (AD-4). Every route is guarded by the session (AD-15): 401 under `/api`, redirection elsewhere; only `/healthz`,
  `/api/auth/*`, `/api/import/v1/*` (Bearer token, AD-103) and, in stub mode, `/connexion-bouchon` are public.
- **Service functions**: the sole implementation of each read and write, with its
  guards (`peutLireSection`, `peutEcrireSection`, `peutVoirFiche`, `fichierLisible` from `services/fichiers.ts`).
  Routes and agent tools call them in the same way (AD-2): this makes human / agent
  symmetry verifiable.
- **Agents**: two tool catalogues, GM and Player, selected on the server according to the
  account's role in the current universe (AD-26, AD-74), behind the `AgentTransport` port (AD-73).
- **Images**: a `GenerateurImage` port, `bouchon`, `aucun`, `codex` adapters (AD-88 to AD-90; AD-45, AD-50, AD-55).

## Import API (`kanevas-import`, target)

> Implemented: context and limits (`GET /`), batches, keyed sheets of every product type,
> file uploads and references, sheet deletion, campaigns, scenarios and relations. Sheet imports
> accept title, PJ, origin dates, keyed sections, aliases, labels, parent, subtype and illustration.
> `compte_rendu` additionally requires a known campaign key. Without `?lot=`, writes leave no batch trace.

**File import** (`kanevas-fichiers-put`): `assurerFichier` in `services/fichiers.ts` implements `PUT /fichiers/:cle` (same `{id, etat: creee|mise_a_jour|inchangee, avertissements}` result as sheets). Send `nom` (1–200 characters) and optional `visibilite` (`joueurs` by default, or `mj`) before the multipart `fichier`. SHA-256 is computed while `stockage.ts` streams the upload; unchanged bytes keep their disk token, changed bytes replace it. `dernier_import` protects the name and visibility independently; each protected field warns in the response and batch. An empty file is a 400 `invalide`, `champ: fichier`, counted as refused with its key and reason, without a stored file. `GET /` adds `limites.fichiersJointsParSection` (100). Files are counted under the batch’s `fichiers` nature.

**File references** (`kanevas-fichiers-references`): `PUT /fiches/:cle` takes `illustration` (image key; a document is a 400 `pas_une_image`), `fichiers` per section (at most 100 keys, else 400 `invalide`, `champ: fichiers`, counted as refused) and `fichier:cle:K` in a text. A known key is rewritten to `fichier:<id>`; an unknown one stays as sent, waits in `fichiers_attente` and warns the batch (never a refusal). When the file arrives (`PUT /fichiers/:cle`), one transaction rewrites the texts and sets the joins and the illustration, then deletes the waiting rows, without touching `version`, `version_importee` or `modifie_le`; a 101st join stays waiting with a warning. The replay compares after resolving known keys; the illustration and the joined files are protected by B-48 (keys in `dernier_import`). The batch closing counts the waiting references with the waiting links (E-18); the GM sees « Fichier en attente d’import » on E-9 (server-side view, AD-96: a reader never receives the key).

**Campaign and scenario imports** (`kanevas-reprise-suivi`, AD-121, migration 0016):
`services/import-suivi.ts` validates requests and counts outcomes through `noterDansLot`;
`assurerCampagne` and `assurerScenario` live beside the ordinary writes they call in
`services/campagnes.ts` and `services/scenarios.ts`. Campaign keys belong to the token's universe;
scenario keys belong to that campaign. `PUT` returns `{id, etat, avertissements}` like sheets.
Replay protects the campaign's name/status and the scenario's title/content separately; unchanged
scenarios keep their version and modification date. An unknown campaign is a counted 404
`campagne_inconnue`; an invalid body is a counted 400 `invalide` with `champ`; a closed batch is
409 `lot_clos`. `GET /` also exposes `nomCampagne: 80`, `titreScenario: 120` and
`contenuScenario: 100000` in `limites`. Scenario Markdown and origin-key links use the existing
reader in `scenarios.ts` (AD-97), resolving keys on read.

**Report and relation imports** (`kanevas-reprise-cr-relations`, AD-121):
`assurerFiche` creates reports through `creerCompteRendu`, without an author, reusing its initial
« Compte-rendu » section for the first imported section. Additional sections use ordinary section
services. A missing or unknown campaign is a counted 400 `invalide`, `champ: campagne`, before any
sheet write. Replay keeps the campaign and creation date, warning when either differs. E-13 uses
that creation date for both display and ordering, under the existing section visibility guard.
`assurerRelations` in `services/import-relations.ts` handles each array entry in its own transaction
through `relierSection`. The response is an array of `{section, cible, type, etat, avertissements}`
with `id` on creation and `code`/`raison` on refusal. States are `creee`, `inchangee`, `ignoree`
(unknown section or target, warning only) and `refusee`. Domain refusals `auto_relation` and
`limite_relations` also appear as `code` in the batch report. E-18 already displays the `relations`
counters; `GET /` exposes `relationsParSection: 100`.

Contract consumed by Monsieur's script, and any other (AD-103, AD-104). Base:
`https://kanevas.berard.me/api/import/v1/univers/:id`, header `Authorization: Bearer kvs_…`. JSON,
camelCase names, ISO 8601 dates. An **origin key** (`:cle`): 1 to 200 characters, without `|`, `]`
or a newline, encoded in the address; chosen freely by the script (`lieu:port-sel`, a Kanka identifier…).
A write carries `?lot=<id>` to be counted; without a batch it succeeds but nothing is counted. Errors: the routes' format (`{message, code}`); 401
`jeton_invalide` (single body); 404 for another universe or an unknown key (except `DELETE /fiches/:cle`, 204 even if unknown); 400 `invalide` with `champ`;
413 for a body over 8 MiB.

## Security

| Threat | Response |
|---|---|
| A player learns that something exists (sheet, section, map, title) | It is absent everywhere; its address answers like an unknown address (AD-22, AD-38). |
| A secret file retrieved by guessing its address | Random disk name; no static route; guard rechecked for every byte served (AD-7, AD-35, AD-36). |

| An illustration stays in a browser's cache after it loses the right to see the sheet | **Accepted risk** (AD-93): `private` cache of the sole browser that already saw it; the sheet disappears from its lists, nothing requests it again, and the server rechecks on every request. *Since `kanevas-import`, the illustration is a media library file: the same risk applies to any file whose visibility changes to « Réservé au MJ » (AD-111); it is no longer “never secret”.* |

## Decisions

**AD-121 — A module registers through a single declaration.** [ADOPTED, decision (e)]
Binds: all modules, B-57 to B-70. Prevents: a module hooking into the router, sidebar, assistant and settings screen in its own way for each.
Rule: a module declares, in a single place, its name, its common settings (stored under the module's name alone), the tools it provides (each: type, scope — one game system or all —, dependencies, default
visibility, uses), its settings and their shape, the shape of its catalogues, its routes, its assistant tools and its interface entry point (loaded on opening,
AD-133). The core knows no module by name. A module groups one or more tools (the `swn` module carries `galaxie` and `vaisseaux`, which share the
jump range setting); activation and visibility are configured **per tool**. *Rejected*: a configuration file per tool — sheet types have none and
the declaration must be testable; *hot loading of third-party code* — Monsieur's decision (5).

**AD-122 — One interface contract per tool type.** [ADOPTED, decision (3)]
Binds: B-59, B-66, B-71, B-75. Prevents: a generator keeping its data separately, a map writing into sections.
Rule: three types, each with a contract tested by a trial module: **dynamic map** (rendered by its module in the « Cartes » section, separate data; the module lists its maps — title, visibility — and E-10 adds them to those in `cartes`, whose shapes do not change), **generator** (the
result is a sheet's managed section, construction choices are tool data attached to the sheet, with the version of the rules and settings), **game
aid** (its own data and entry point; none in this epic). Each contract says how it handles a changed setting (AD-128). A type is added when a second
need resembles the first, not before. *Rejected*: a single generic engine — it would carry SWN's abstractions (decision (1)).

**AD-123 — Tool data lives in the database, in its module's tables, at two levels.** [ADOPTED, decisions (4), (d), point 6]
Binds: every module. Prevents: a file or generic JSON table losing links and queries; access from outside the module.
Rule: prefixed tables, created by the module's migrations, a row attached to a universe (or to a system for its catalogue), sheet references by identifier,
no SQL outside the module's functions; storage organization (typed tables, documents with a declared shape, or both) is the module's choice. The **system** level (the game) and the
**universe** level (the campaign): a universe sees both, universe data with the same key replaces system data, and a universe **removal** (a system key
marked absent for that universe) erases it from its view without touching the system. A system catalogue has no hidden items; a universe item carries
`masque` (GM only), set and cleared by a GM of the universe, and reads filter it for a player like a secret system (B-62, Monsieur's decision of 2026-10-17).
Resolution is **by key, once**: the universe item if it exists (hidden or not), otherwise the system item if not removed; a hidden replacement
never lets the system item reappear, and computation uses only the resolved item.
*Rejected*: hiding a system item (the system is the game, shared by its universes: to make it absent from a campaign, remove it). The contract requires: key, version, attachment, shape declared
and checked on import. *Rejected*: files on the volume; generic JSON table.

**AD-124 — A common API framework, routes specific to each module.** [ADOPTED, decision (e)]
Binds: B-58, B-65, B-61. Prevents: different error and activation conventions per module.
Rule: a module's routes live under `/api/univers/:id/outils/<module>/…` and `/api/systemes/:id/outils/<module>/…`; **activation is checked on entry** (tool
disabled or invisible to the role = unknown address, same response as an absent route); same identities (session for the screen, tool-scoped token for scripts), same
conventions (error `code` + field, pagination, version against concurrent writes, update by key); the module receives the actor, their role and player mode. Two routes
are common to every module: the tool's **description** (settings and their shape, dependencies, activation: E-20 reads it) and **catalogue import** (preview then application,
added / modified / refused report). Screen, API and assistant go through the **same functions** of the module (thin routes, AD-2).

**AD-125 — Activation, visibility and settings resolve system → universe.** [ADOPTED, decisions (6), point 3, point 10]
Binds: B-57 to B-60. Prevents: three places deciding who sees a tool, and settings read in different places.
Rule: a single function resolves, for (universe, tool), the *enabled* state, visibility by role and each setting's value: the universe row if there is one, otherwise the system row,
otherwise the declared default. The system's **responsible** (creator by default, transferable role) alone writes at system level; any GM writes at their universe's level; the instance
admin has no access. Disabling at system level hides the tool from universes following it; a universe that forced it keeps access, including system data. *Rejected*: “any GM of an attached
universe configures the system” (the action affects all universes); *the instance admin as responsible* — they have no content access (AD-9). Templates keep their current rule.

**AD-126 — Tool permissions have two levels, enforced in services.** [ADOPTED, decision point 3]
Binds: B-59, B-73. Prevents: a tool leaking a secret in player view (search, route, zone, menu).
Rule: (1) the core decides whether the tool is **visible** (enabled, visible to the role); otherwise it is not found. (2) The tool declares its **uses** and enforces its internal permissions down to the row,
with Kanevas's permission functions and vocabulary (GM only, players, author, Player mode). “What the account cannot read does not exist for it” applies to the map (item by item),
search, journeys, block generation (AD-132), the assistant and links. The actor never has more permissions than the account; a GM's Player mode reduces them to a player's.

**AD-127 — A section “managed by a tool” is a content lock, separate from the author.** [ADOPTED, decisions (g), (h), (i), (j)]
Binds: B-66, B-67, B-74, B-77. Prevents: two writers of the same section; a player writing beyond their permissions; a section unreadable without the tool.
Rule: the section carries `gere_par`; only that tool's write function, which **goes through the existing section write path** (`ecrireContenu`, with the read version; AD-48), changes its content;
the editor and section API refuse it to anyone else. The tool checks the use and the account's author role (“the author writes”) and writes **on behalf of the account**. Each tool section has **structured content**
in the declared format, a display component supplied by the module (loaded only when a sheet contains one), and a **mandatory text version (Markdown)**, produced with the content and placed in
`contenu`: this is what search, the assistant, export and the sheet read when the tool is disabled. Same audience switches as any section. Kanevas has no sheet owner:
authorship is per section. *Rejected*: the sheet as the generated unit (a sheet mixes managed and free sections).

**AD-128 — A source change rewrites nothing silently.** [ADOPTED, decision (7)]
Binds: B-67, every generator. Prevents: a ship whose numbers change under the player after a setting changes.
Rule: a computed result keeps the version of the catalogue and settings that produced it; when they differ from the current ones, it is marked **stale** (state computed on read, never stored) and is
recalculated on an explicit action, or on a proposal (same mechanism as the update proposal, AD-79), according to what the tool declares. A validated turn (later) is frozen.

**AD-129 — Editable tool data is protected like a section.** [ADOPTED, decision point 11]
Binds: B-64. Prevents: a silent overwrite between two GMs.
Rule: all editable tool data carries `version`; a write supplies the read version; a stale version is refused with the same response as a section (`conflit`, code `donnee_modifiee`), the screen
explains and offers to reload. A managed section is already protected. No lock or live editing.

**AD-130 — A catalogue is a transport JSON file; the database stores it.** [ADOPTED, decision (b)]
Binds: B-61, B-65, B-79. Prevents: an import overwriting, duplicating or deleting without saying so.
Rule: one file per module, one section per item kind, each item a **key**; the file is checked against the module's schema **before** being applied (invalid item refused with its field, the
rest goes through); reimport = update by key without duplicates; an item removed from the file is not deleted; the catalogue has a version, which a result keeps (AD-128). Two paths, same functions: the « Outils » tab
(preview then application) and the extended import API with a **tool-scoped** token (batch report by kind). Like B-48, an import does not overwrite what a human has since modified in Kanevas. A token belongs to a universe: it writes the **system's** catalogue only if its account is its maintainer at that moment (the role is reread on every use, like an import token's GM role).

**AD-131 — Nothing from Éneria enters the public repository, including tests.** [ADOPTED, mandate letter]
Binds: B-78, B-79. Prevents: a catalogue from the book, a translated rules sheet, a value computed from real data, a screenshot, entering `kanevas` or its public logs.
Rule: the public repository contains only the **format**, the code reading it and a small **invented** trial catalogue (with its own expected values, computed by hand or by the module's rules); the attested
suite and `kanevas` CI run on this synthetic data alone (Monsieur's decision, 2026-10-16). Tests on real data, their reference values (computed once with Monsieur's current tools, frozen) and the conversion script live in `AntorFr/eneria`, directory
`_outils/kanevas/`, and run **in the pods**, which read `eneria` with their existing access: they exercise `kanevas` code at a pinned revision, outside the attested suite. A discrepancy is a porting bug or a decided and recorded rule correction. *Rejected*: a `kanevas` “tests” workflow with a private repository secret — Monsieur's decision of 2026-10-16: CI is public, as are its logs; *anonymized real data* — the test's value lies in the exact data.

**AD-132 — The map is infinite: anonymous systems are computed server-side, in blocks.** [ADOPTED, point 9]
Binds: B-71, B-73. Prevents: a client receiving the whole map; a secret territory inferred from the generated density.
Rule: a block of 5×5 hexagons is generated from coordinates and a seed (same location, same result, tested) **server-side**, under the caller's permissions: density takes into account
only territories this account can read; the result is cached (memory). Only defined systems, routes, zones and **promoted** anonymous systems are stored (they keep their location and become
universe data with its permissions). The **seed** (specific to each galaxy, protected): changing it requires confirmation explaining that all undefined systems change location. The view receives only the blocks it displays. *Outside scope*: the offline map.
*Resolved by `kanevas-outils-galaxie-lire` (G-4)*: the key carries the reading level (`mj` / `joueur`, Player mode being `joueur`) and a fingerprint of the readable zones; the cache holds generated positions only.

**AD-133 — Tool code loads when used.** [ADOPTED, point 9]
Binds: B-70. Prevents: a bundle carrying the map and designer for all accounts; a data.js sent in full.
Rule: a module's entry point and a section's component are loaded through a dynamic import, on opening the screen or when a sheet contains the section; an account without access never loads it; data
follows the view (AD-132). A component respects the existing conventions (tokens in `frontend/src/ui/tokens.css`, `docs/charte.md`) and is exercised at 360 px width. Each tool's acceptance criterion: phone and tablet.

**AD-134 — A shareable link leads to a stored resource.** [ADOPTED, point 8]
Binds: B-68. Prevents: content encoded in the address bypassing permissions and the catalogue version.
Rule: the address of a map system or ship sheet is a stored identifier; it is read according to the opener's permissions (unreadable = not found). No content is encoded in the address.
Printing is a later core function for any sheet (outside the epic).

**AD-135 — Disabling hides; deleting is a separate action.** [ADOPTED, point 6]
Binds: B-63. Prevents: data lost by clicking a toggle.
Rule: disabling a tool touches no row; it hides the entry point, addresses, data and the view of system data for the universe; its managed sections remain readable in text form with an
« outil désactivé » banner, without regeneration or modification. Deleting data is a separate, restricted function (the responsible for the system, GM for the universe), whose confirmation counts what goes and, for the system,
what still uses it (universes, local items, designs). Deleting a universe erases its tools' data (one transaction, including the module's tables).

**AD-136 — A tool's capabilities for the assistant are neutral module tools.** [ADOPTED, model (8)]
Binds: B-69. Prevents: an assistant more permissive than the screen; a tool visible to a role that does not have it.
Rule: a module declares assistant tools in `catalogue`'s shape (`{nom, description, schéma, executer}`), composing only module functions (AD-27); `catalogueDe` adds them when the tool is enabled and visible
to the role read from the database; account, universe and role are closed over, never a parameter; a refusal returns `{ok:false}` without an event.

**AD-137 — Two modules talk through their functions, on a declared dependency.** [ADOPTED, decision (e)]
Binds: every module. Prevents: a module reading another's tables or calling it over HTTP.
Rule: a dependency is declared in the declaration (AD-121), the activation screen enforces it (B-58); the call goes through the other module's exported function, under the same permissions. In this epic, there is no dependency between tools: `vaisseaux` reads the jump range configured at `swn` module level, not the map. The mechanism is tested with the trial module.

### Detail of `kanevas-outils-cadre` (the framework slice)

Decisions of this slice, taken inside AD-121 to AD-126, AD-133, AD-136 and AD-137 (they amend none). Marked **C-n**.

**A numbering collision, noted.** `AD-121` is used twice in this file: by `kanevas-import-reprise` (campaigns, scenarios, session reports and relations through the import API, in the code at `services/campagnes.ts` and `scenarios.ts`) and by the tools framing (« A module registers through a single declaration »). The framing was validated with its numbers and renumbering it would rewrite the decision Monsieur read; this slice therefore always writes **« AD-121 (module declaration) »** and its tasks cite it that way; `git grep 'AD-121 (module'` finds it. Cheapest to undo: renumber the tools decision to the next free number in a later pass.

**C-6 — The sidebar refresh (AD-133).** E-20 and the bar are two tasks; their contract is one browser event: after every successful write of `PanneauOutils` (activation, visibility, settings, transfer) it dispatches `window.dispatchEvent(new Event('kanevas:outils-modifies'))`; the bar listens and re-asks `…/outils/entrees`. The event name is the whole interface. The bar's task tests it by dispatching the event itself after a `PUT`; the tab's task tests that each write dispatches it.

**Files.** `src/outils/declaration.ts` (the types below and their zod check), `src/outils/registre.ts` (`modulesActifs()`: the list of modules; the `essai` module is in it only under `KANEVAS_STUB=1` or `NODE_ENV=test`, read in `config/env.ts` like the other switches), `src/outils/essai/` (the trial module: `index.ts` declares it, one file per tool), `src/services/outils.ts` (**the only reader and writer of `outils_systeme` and `outils_univers`**, and of `systemes_jeu.responsable_id` for the transfer), `src/routes/outils.ts` (thin routes, AD-2). Frontend: `frontend/src/outils/registre.ts` maps `module/outil` to a lazy import of its screen; `frontend/src/ecrans/outils/` holds E-20. One migration of the core, numbered when the slice merges (AD-51): the two tables of `docs/donnees.md` and `systemes_jeu.responsable_id` (nullable, no backfill).

The core implementation uses migration `0017-outils.sql` (provisional number). Its three write services
take `(db, acteur, cible, cle, valeur)`, where `acteur` is an account id or an `Acteur` and `cible` is
`{ niveau: 'systeme' | 'univers', id }`; settings take `{ version, valeurs, confirme? }` as their value.
`resoudreOutilSysteme` exposes the base resolution for the system settings screen; `resoudreOutil`
exposes the universe resolution. Both return common settings as `communs: { reglages, versionReglages }`.
`responsableEffectif` computes ownership without changing the stored account; `exigerOutil`,
`exigerUsage` and `listerCartesOutil` compose activation, role and item visibility checks for module callers.

**The declaration (AD-121).**

```
DeclarationModule { nom, libelle, reglagesCommuns: Reglages, outils: DeclarationOutil[], routes?(app, garde) }
DeclarationOutil  { cle: 'module/outil', libelle, description,
                    type: 'carte' | 'generateur' | 'aide',
                    portee: 'tous' | { noms: string[] },      // game systems it applies to (C-1)
                    dependances: string[],                    // keys of other tools of the same module
                    visibiliteParDefaut: { mj: boolean, joueur: boolean },
                    usages: { nom, mjSeul: boolean }[],
                    reglages: Reglages,
                    outilsAssistant?(ctx): OutilAssistant[],  // AD-136
                    ecran: { libelle, icone }  }              // sidebar entry, AD-133
Reglage           { libelle, aide?, niveau: 'systeme+univers' | 'univers',

```

`verifierDeclaration` runs at startup and in the unit tests: unique keys, dependencies that exist in the module and form no cycle, a default inside its own shape, at most one tool of a key. A malformed declaration stops the server (a developer's error, never a user's). The core imports no module by name: it reads `modulesActifs()`.

**C-1 — Which systems a tool applies to.** `portee: 'tous'` (every game system) or `{ noms }`, names compared after trimming and case-folding. The system has no stable key (`systemes_jeu` carries a name); the SWN tranches choose between the two. *Cheapest to undo*: a key column on `systemes_jeu` replaces `noms` later without touching any stored row. The trial module uses `'tous'`; the unit test covers `noms`.

**Resolution (AD-125).** `resoudreOutil(db, universId, cle)` is the one function; it returns `{ active, visibilite: { mj, joueur }, reglages: { [nom]: { valeur, origine: 'defaut' | 'systeme' | 'univers' } }, versionReglages: { systeme, univers } }`. For each field: the universe row if it is non-null, else the system row, else the declared default (a tool is *disabled* by default). A setting of `niveau: 'univers'` ignores the system row. The common settings of the module (row `outil = '<module>'`) resolve the same way and are returned apart, under `communs`. `accessible(db, acteur, universId, cle)` answers whether the tool is **enabled and visible to the actor**: the role read from `membres` at each call, `visibilite.mj` for a GM outside Player mode, `visibilite.joueur` for a player and for a GM in Player mode; no role = no. **A tool the actor cannot use is `introuvable`** (same response as an unknown address). The tool's own check `peutUsage(acteur, cle, usage)` then applies its declared `usages` (an `mjSeul` usage is refused to a player with `refuse`).

**C-2 — Who writes where (B-57).** `exigerResponsable(db, compteId, systemeId)`: the account is `responsable_id`; when it is null, any GM of a universe attached to the system. Anyone else: a GM of an attached universe who is not the responsible gets `refuse` on a write and reads; an account that is no GM of an attached universe (player, foreigner, instance admin as such) gets `introuvable`. Universe-level writes: `exigerMJ` of the universe. A GM in Player mode has no write (like every service of the product). `creerSysteme` and `creerEtRattacherSysteme` set `responsable_id` to the creator. `transfererResponsabilite(db, compteId, systemeId, versCompteId)`: the caller is the responsible (or any GM when there is none); the target must be a GM of an attached universe, else `invalide` with `champ: 'compte'`; the former responsible keeps their GM role in their universes and loses the system level only. If the responsible account is deleted, `ON DELETE SET NULL` brings the system back to the rule without owner.

**C-3 — Writes.** Three separate service functions per level, so that none rewrites the others: `poserActivation(…, active)` (system: `true`/`false`; universe: `true`/`false`/`null` = follow), `poserVisibilite(…, { mj?, joueur? })` (system: booleans; universe: booleans or `null` = follow), `poserReglages(…, { version, valeurs })` (a value `null` removes the universe override; a system value is never null). Only the settings write bumps `version_reglages` of its row (AD-128: activation never makes a design stale); a stale `version` is `conflit` with `detail: 'version'`. A value outside its shape is `invalide` with `champ` = the setting's name; an unknown setting or a setting of another level is `invalide`. A protected setting (`protege`) is written through the same function but the route requires `confirme: true` in the body, else `invalide` with `code: 'confirmation_requise'` (the screen of the tool shows the confirmation; the trial module has none).

**C-4 — Dependencies (AD-137, B-58).** Activating a tool *at a level* requires every dependency to be effectively active **at that level** after the write (system: system rows; universe: the resolved value for the universe); otherwise `conflit`, `detail: 'dependance'`, message « <Outil> demande <autre outil> : activez-le d'abord. ». The reverse is guarded too: turning a tool off while a dependent is active at that same level is refused with « <Autre outil> demande <Outil> : désactivez-le d'abord. » (`detail: 'dependant'`) — cheaper than a tool left active over a missing one; undone by dropping the check. A dependency never reads another module (AD-137): the trial test only checks the enforcement.

**C-5 — Common API (AD-124).** All under the session guard; errors `code` + `champ` as in `kanevas-import`.

### Detail of `kanevas-outils-galaxie-lire` (the galaxy map, read side)

Decisions of this slice, taken inside AD-122, AD-123, AD-126, AD-132, AD-133, AD-134 and AD-136 (they amend none). Marked **G-n**. It builds on the framework of `kanevas-outils-cadre` (declaration, `garde`, `accessible`, `resoudreOutil`, the `carte` contract); where it needs one more field of that contract it says so (G-8).

**G-1 — Files and layers.** SQL and guards live in `src/services/swn/` (AD-2: only `services/` reads or writes tables): `galaxies.ts` (galaxies, reading level, the row filters of G-2, listing for E-10), `lecture-carte.ts` (view by blocks, system, search), `trajet.ts` (journey), `cache-blocs.ts`. The rules are **pure functions without SQL or clock** in `src/outils/swn/regles/`: `hex.ts` (axial coordinates, distance, hexagon to pixel and back, polygon test), `generation.ts` (blocks), `chemin.ts` (shortest path and duration), `format.ts` (« 4,5 jours »). `src/outils/swn/index.ts` is the module declaration (`nom: 'swn'`, `portee: 'tous'`: `systemes_jeu` has no key, so the module applies to every game system and, in stub mode, to « Système d'essai »; one tool `swn/galaxie`, type `carte`, `visibiliteParDefaut {mj: true, joueur: true}`), `src/outils/swn/routes.ts` the module routes, `src/outils/swn/assistant.ts` the assistant tool. Frontend: `frontend/src/outils/swn/galaxie/` behind the registry of `frontend/src/outils/registre.ts` (dynamic import, AD-133). The migration takes its number at merge (AD-51) and creates the four tables of `docs/donnees.md` **complete** (including the columns `kanevas-outils-galaxie-tenir` writes: `fiche_id`, `section_id`, `version`), so that slice adds no migration for them.

**G-2 — Reading levels.** `niveauLecture(db, acteur, universId)` is the one place a role becomes a level: `'mj'` (a GM outside Player mode), `'joueur'` (a player, and a GM in Player mode, `?mode=joueur` read by the common pre-handler), `null` (no role, tool not `accessible`: everything answers `introuvable`). A galaxy that is not `visible` is `introuvable` at level `'joueur'` for a player; for a GM in Player mode it is `refuse` with `detail: 'mode_joueur'` (same convention as `lireCarte`). Row filters, written once in `galaxies.ts` and used by **every** read (view, system, search, journey, assistant, cache): level `'joueur'` sees systems `secret = 0`, zones `secret = 0`, routes `publique = 1` **whose two ends are visible systems**; level `'mj'` sees all. No function returns a count of what is filtered out.

**G-3 — Generation of a block (AD-132).** Pure: `bloc(graine, bx, by, champDensite) → {q, r}[]`. Block `(bx, by)` holds the hexagons `5·bx ≤ q ≤ 5·bx+4`, `5·by ≤ r ≤ 5·by+4` (`bx = floor(q / 5)`, so negative coordinates work). For each hexagon, `u = first 6 bytes of SHA-256("<graine>:<q>:<r>") / 2^48` and a system exists when `u < densite(q, r)`; the same `u` for the same triple, on every machine and every restart (tested with literal expected positions for a fixed seed on the trial data). **Density** of a hexagon: among the zones *readable at the caller's level* that contain its centre (polygon test), the **lowest** `densite` (a zone with `densite` null is ignored for this purpose); none: the galaxy's `densite_defaut`. The *defined* systems are **not** consulted: a defined system replaces the generated one on its hexagon **at read time**, only if the caller can read it. So a secret system's hexagon shows, for a player, exactly what it would show without that system. An anonymous system has no name, no link and no stored identity until promoted (`kanevas-outils-galaxie-tenir`); the panel shows « Système non défini » and its coordinates. *Cheapest to undo*: the density rule (lowest wins) is one function.

**G-4 — The block cache key (resolves the [TO VERIFY] of AD-132).** The cache holds only the *generated* positions of a block, never defined data (read fresh at each request under G-2). Key: `(galaxie_id, graine, bx, by, niveau, empreinte)` where `niveau ∈ {'mj','joueur'}` is the reading level of G-2 and `empreinte` is the SHA-256 of the sorted `(cle, version)` of the zones readable at that level — computed at each request (a galaxy has dozens of zones), so editing, adding or removing a zone, or changing the seed, changes the key and a stale entry is simply never asked again. Player mode and ordinary players share `'joueur'`: there is **no per-player knowledge** (mandate decision), so the key cannot be finer without being useless, and cannot be coarser without leaking. Memory only, least-recently-used, 4 000 entries. `cache-blocs.ts` exports `viderCacheBlocs()` and a `compteurs()` (hits, generations) for tests. *Tests*: Antor warms a block, Léa reads it with zero extra generation of a `'mj'` entry and equal to her cold read; a block under a secret zone is identical for Léa with and without the zone (the zone added then removed in the test).

**G-5 — Journey (B-72).** Pure `chemin.ts`. Lengths come from the stored `longueur` of readable routes (undirected). With engine `n` (integer 1–6, chosen on the screen, default 2), the **range** of a leg is `p × (n + 1)` cases where `p` is the module's common setting `portee_saut` (cases per engine level, integer 1–20, default 5, `systeme+univers`: the book's `5 + 5n`). A route longer than the range **is not usable** (it is not cut in two). Shortest path: Dijkstra on total length over usable routes; ties by fewer legs, then by the lexicographic list of system `cle`s (deterministic). **Duration** = Σ over legs of `longueur / n + 1` days (one day of transit per leg: the rule of Monsieur's current tool, « Theryn → Éneria, 7 cases, engine 2 = 3,5 + 1 = 4,5 jours »). Shown rounded to the nearest tenth, half up, comma as separator, trailing « ,0 » dropped, « 1 jour » singular below 2: `« 7 cases · 4,5 jours »`. *Hexagon distance* (measurement, E-21) is `(|Δq| + |Δr| + |Δq+Δr|) / 2`. `routes` = `toutes` is honoured at level `'mj'` only; at `'joueur'` it behaves as `publiques` (no error, no signal). A departure or arrival that is not a readable system is `introuvable`; no usable path is `{ trouve: false }` with one fixed text « Aucun trajet avec ce moteur. », never saying whether a hidden route, or a stronger engine, would give one. *Rejected*: minimising duration instead of length (the book's tool minimises length; both agree on the reference cases, length is the decided behaviour).

**G-6 — Routes (AD-124, AD-126).** Module routes behind `garde('swn/galaxie')`, under `/api/univers/:id/outils/swn/galaxie/`, all `GET`, thin over the services:

| Route | Gives |
|---|---|
| `galaxies/:gid` | `{ id, titre, visible, version, niveau, porteeSaut, reference }` (`niveau` lets the screen show GM controls later; `visible` only for `'mj'`; `reference` is `{ cle, nom, q, r }` or null — the galaxy's first *readable* defined system by identifier, computed at the caller's level, so the screen can write « 7 cases depuis Port-Sel » whatever blocks are loaded; a secret system is never the reference of a player) |
| `galaxies/:gid/blocs?de=bx,by&a=bx,by` | the rectangle of blocks, at most 12 × 12 (`invalide` above): `{ blocs: [{bx, by, generes: [[q, r]…]}], systemes: [{id, cle, nom, q, r, taille, couleur}], routes: [{id, depuis: {cle, q, r}, vers: {cle, q, r}, longueur, publique?}], zones: [{id, nom, contour, couleur, secret?}] }`: systems inside the rectangle, routes with at least one end inside, zones whose bounding box meets it; `publique` and `secret` only at level `'mj'` |
| `galaxies/:gid/systemes/:cle` | the panel: `{ nom, q, r, taille, couleur, notes, routes: [{ « avec »: {cle, nom}, longueur }], lien }` (`lien` = the stable address, G-7); notes as plain text |
| `galaxies/:gid/recherche?q=` | among readable systems, name containing the text after folding case and accents, 20 at most, ordered by name; `q` under 2 characters: empty list |
| `galaxies/:gid/trajet?depart=<cle>&arrivee=<cle>&moteur=<n>&routes=toutes\|publiques` | `{ trouve, etapes: [{cle, nom, q, r}], troncons: [{depuis, vers, longueur, jours}], cases, jours, libelle }` |

Every unknown, hidden or foreign identifier is the same 404 as an unregistered path (compared byte for byte in the tests, as `cadre` does). The view carries no more than the requested rectangle; there is no « whole galaxy » route.

**G-7 — The address of a system (AD-134, B-68).** `/univers/:id/outils/swn/galaxie/:gid?systeme=<cle>`: the stored identifier is the system's `cle` (stable across a re-import: the import keys every element by `cle`). Opening it loads the galaxy, centres on the system and opens its panel; a `cle` the caller cannot read gives the same « Page introuvable. » as a missing one. The screen keeps `?systeme=` in sync with the selection (history `replace`), so the address bar always holds a link to read. Nothing but the two identifiers is in the address (no coordinates, no name).

**G-8 — E-10 lists the galaxies; the `carte` contract gains an `id`.** `cadre` declares `cartes?(db, acteur, universId) → { titre, visible }[]`; this slice makes it `{ id, titre, visible }[]` (and amends `cadre`'s contract test) so that the entry has an address. The core function `listerCartesOutils(db, acteur, universId)` (in `services/outils.ts`) walks the active modules, keeps those whose tool is `accessible` for the actor and returns `{ module, outil, id, titre, visible }`; a player gets only visible ones. The route that lists maps for E-10 appends them with `type: 'outil'` and the address `/univers/:id/outils/:module/:outil/:id`; the core knows no module by name (AD-121 (module declaration)). The tool's screen is `OutilEcran` of `cadre`, which resolves the path segment after the tool to the module's component props `{ galaxieId }`.

**G-9 — Assistant tool (B-69, AD-136).** `swn_galaxie_trajet({ galaxie?, depart, arrivee, moteur?, routes? })`: names, not identifiers; `galaxie` optional when the actor reads exactly one (none readable: `'Introuvable.'`; several: `{ ok: false, erreur }` with the message « Précisez la galaxie. », which lists nothing); a system name is matched after folding case and accents among **readable** systems; none or several: `{ ok: false, erreur: 'Introuvable.' }` / `'Plusieurs systèmes portent ce nom.'` (the second says nothing about hidden ones: ambiguity is computed on readable systems only). The result is the object of the route above, so that screen and assistant agree. Actor `{compteId}`, no Player mode (as every assistant tool); never an `evenement`. Declared by `outilsAssistant` and present in `catalogueDe` only when the tool is `accessible`.

**Data additions (see `docs/donnees.md`).** Two columns beyond the framing's table, both needed by G-3: `swn_galaxies.densite_defaut` (real, 0–1, default 0.2) and `swn_zones.densite` (real 0–1, null = no effect on density). Coordinates are integers with `CHECK (abs(q) <= 100000 AND abs(r) <= 100000)`. A zone's `contour` is a JSON array of `[q, r]` vertices of a simple polygon in axial coordinates (closed implicitly). The test is made **in axial coordinates**, the centre of a hexagon being its `(q, r)` itself: the axial-to-plane map is linear, so containment is the same in either frame and no conversion is needed; a centre exactly on an edge or a vertex counts as **inside** (tested: the secret system of the trial galaxy, on the edge of « Marches interdites »). *Cheapest to undo*: columns with defaults, no stored data derived from them.

**The trial galaxy and the stub seed.** « Galaxie d'essai » in « Éneria d'essai » (`visible`, seed `essai-1`, `densite_defaut` 0.2): systems « Port-Sel » (0, 0), « Vael » (7, 0), « Hesper » (1, 5) and « Station fantôme » (−4, 2, `secret`); routes Port-Sel–Vael (7 cases, public), Vael–Hesper (6, public), Port-Sel–Hesper (6, **private**); zone « Marches interdites » (secret, `densite` 0, contour `[[-12,2],[-4,2],[-4,8],[-12,8]]`). All invented. Expected by hand, written in the tests: Port-Sel → Vael, engine 2, public: `7 cases · 4,5 jours`; Port-Sel → Hesper, engine 2: Antor (all routes) 6 cases, `4 jours`; Léa (public) via Vael 13 cases, `8,5 jours`; with engine 1 (range 10) Léa's path is still 13 cases and `15 jours` (7 and 6 are within range); the « no path » case is tested by adding in the test a 12-case route as the only link and engine 1 (12 > 10).

**Interface (AD-133).** One SVG with pointy-top hexagons in axial coordinates; pan by pointer drag, zoom by wheel and pinch (Pointer Events, two pointers), hexagon size 10–60 px, the lowest zoom such that at most 60 × 60 hexagons (12 × 12 blocks) are visible. The view computes the blocks it shows, asks the missing ones (debounced 150 ms, at most 4 requests in flight), keeps them in memory keyed by `(bx, by, niveau)` and drops those far from the view; a change of Player mode empties the store. Labels collapse below a zoom threshold and are truncated at 24 characters on the map (the panel shows the full name, 80 at most). Hover (mouse) or a tap (touch) on a system shows its name and distance in hexagons from the reference system (the one chosen as departure, else the `reference` of the galaxy's answer, G-6 — chosen because the exit criterion asks for a distance before any departure is chosen). Touch targets are at least 44 px (the maquette's `.t`); below 760 px the panels are under the map. Colours come from `frontend/src/ui/tokens.css` only; a system's `couleur` is one of the palette's named colours, never a free value (the column holds the name; the write is `galaxie-tenir`).

**Tests.** Pure: hexagon distance and conversion (round trip), generation (literal positions for a fixed seed, same call twice, negative coordinates, density 0 and 1), density by lowest zone, journey (the by-hand cases above, tie-break, range, no path), duration formatting (4,5 / 4 / 8,5 / 1 jour). Services on a temporary database with the stub seed: G-2 matrix (Antor, Mira, Léa, Roxane, a foreigner, Antor in Player mode on a visible and on a hidden galaxy), search never finds « Station fantôme » for Léa, a route to a secret system added in the test is absent from her view, journey and panel, the generated block over the secret hexagon equal with and without it, the cache (G-4). Routes: the table of G-6, the 404 compared byte for byte, a tool disabled or invisible. Assistant: same result as the route, absent when the tool is invisible, `{ok:false}` without event. Screen: Chromium at 390 px (see `docs/ecrans.md`).

## Security

The threat: a GM secret (hidden system, private route, territory, hidden design) reaching a player through the map, search, a journey, generated density, a link, the API or the assistant. Countermeasures:
item-by-item permissions in module functions (AD-126), server-side generation under permissions (AD-132), invisible tool = not found (AD-124), tool-scoped token, locked managed section (AD-127). No Éneria secret in the public repository or its logs (AD-131).

## Stubs

No new dependency requiring a token, account or authentication: modules make no external call. The assistant keeps its stub (`KANEVAS_STUB=1`, AD-78), whose script can call modules' assistant tools.
Acceptance runs in stub mode, on the invented trial catalogue.
