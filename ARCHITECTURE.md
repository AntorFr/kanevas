# Architecture — kanevas

RPG management system (lore, campaigns, session reports, permissions, maps). What it enables,
for whom and through which screens: `docs/parcours.md`, `docs/ecrans.md`; its data: `docs/donnees.md`.

This document has two parts: **today**, the map of the code as it stands; **the target**,
the architecture of the whole product, set by the epic's scope and implemented slice by
slice (on `main`, the target describes only what has been built).

# Today

Since `kanevas-premiere-fiche`, the foundation (one Fastify application, Node 20, TypeScript,
`GET /healthz`, an OIDC mechanism, an image published by CI) carries the **first business
function**: accounts, universes, members, sheets and sections, with their permissions; sessions
and stub mode; the React frontend that displays them (home, universes, members, lore, sheet).
It also includes the game system and, with `kanevas-suivi`, session tracking: campaigns, scenarios,
preparation, session reports; `kanevas-relier-chercher`, relations between sheets and search (within a type, then across all types since `kanevas-import-recherche`; FTS5 indexes, AD-63, AD-64, AD-118); attachments (storage on the volume, E-9 block);
`kanevas-assistant-membre`, each member's assistant: a conversation panel whose tools
call the same service functions as the routes, with the person's permissions (AD-73 to AD-78).
Maps and graphs (E-10, E-11) are built. `kanevas-monde` adds a proposed section update based on a session report, which the GM applies or abandons with one action (AD-79 to AD-82); `kanevas-images` adds generation of a portrait attached to a section (AD-88 to AD-90).
`kanevas-recours-admin` adds instance administration (E-5, AD-86, AD-87).

## Routes `/api`

All guarded by the session (401 without a session), except `/api/auth/*` and `/api/import/v1/*`, which opens only with a Bearer token (AD-103) and ignores the cookie. Service errors are
`introuvable` 404, `refuse` 403, `invalide` 400, `conflit` 409 (`section_modifiee`, `nom_pris`, `gabarit_modifie`, `scenario_modifie`, `proposition_appliquee`, `relation_existante`, `limite_relations`, `limite_pieces`: 100 attached files per section (AD-111) — 409 for a GM, 403 `refuse` for another member (AD-117), `fiche_deja_placee` and `carte_pleine` for maps; 413 `fond_trop_lourd` for a background over 25 MB; 400 `fichier_vide` for an empty attachment (an empty map background is a 400 `fond_invalide`); `auto_relation` is a 400 `invalide`). Removing the last
GM returns `invalide` 400 with the reason; so does section content over 100,000 characters (AD-91). A service error body is `{message}` (plus `code` when the service supplies one); an `/api/...` address with no matching route (for example a route removed by AD-94) returns 404 with the « Page introuvable. » HTML page, rather than JSON. The server listens on `0.0.0.0` (`-p 3001:3001` suffices).
In stub mode, `POST /connexion-bouchon` expects a form-urlencoded body `compte=<identifiant>`.
The rows citing AD-93 or AD-94 belong to `kanevas-illustrations`, built by that slice;
they replace the old `GET /api/univers/:id/systeme` and `…/systeme/gabarits*` routes.

Request bodies (JSON): `POST /api/univers` `{nom, description?}`; `POST .../membres`
`{username, role}` (`role`: `mj` \| `joueur`; `username` is the exact identifier); `PATCH
.../membres/:compteId` `{role}`; `POST .../fiches` `{type, titre, charge?}` (`charge`: object, optional unless the type requires it — `personnage` needs `{"pj": bool}`, `compte_rendu` a `campagne_id`; shapes in `docs/donnees.md`);
`POST .../sections` `{titre, contenu?}` (`contenu`: text, same ceiling; the screen sends only `titre`); `PUT .../ordre` `{ids}` (all the sheet's section ids);
`PATCH .../sections/:sid` `{titre?, joueursLisent?, joueursEcrivent?, auteurLit?, auteurEcrit?,
auteurId?}` — `auteurId` is the **numeric account id** (members' `compteId`), `null` for
no author; `PUT .../contenu` `{contenu, version}`. API names use camelCase, database names
snake_case (`docs/donnees.md`).

## Invariants

- **The version has a single source**: the Docker build-arg `APP_VERSION`, derived
  by CI from the pushed semver tag (outside a tag, the value is not a semver: only an image built
  from a tag carries one). `/healthz` and the published image tag therefore
  cannot diverge. `package.json` deliberately has no
  `version`.
- **`/healthz` is public** (alongside `/api/auth/*` and login pages, AD-15), as plain text `kanevas <version>`, without data.
  `GET /api/auth/config` (`{oidcEnabled}`) is public too; no other public
  route exposes content.
- **The OIDC callback authenticates an identity, nothing more**: it opens a session carrying
  the identifier and groups, and creates the account; **no universe role comes from Authelia**
  (AD-9), it is read from the members table on every request. Without the four
  `OIDC_*` variables (or with only some of them), login and callback return 404; an empty
  or invalid value causes startup to fail.
- **Twenty-six tables and two search indexes, no ORM**: `comptes`, `univers`, `membres`, `fiches`, `sections` (migration
  0001), `systemes_jeu`, `gabarits` (migration 0002), `campagnes`, `scenarios`, `taches_preparation` (migration 0003), `pieces_jointes` (migration 0004, emptied by 0015 and no longer read), `relations`, `recherche_fiches` and `recherche_sections` (FTS5, migration 0005); three illustration columns on `fiches` (migration 0006), `cartes` and `elements_carte` (migration 0007), `propositions` (migration 0008, `kanevas-monde`); `jetons_api` and `lots_import`, plus source keys on `fiches` and `sections` (migration 0010, `kanevas-import-fil`); `sections.contenu_public` and the rebuilt `recherche_sections` index (migration 0011, `kanevas-import-secrets`, AD-114); `liens` (migration 0012, `kanevas-import-liens`, AD-116); `types_systeme` and `types_univers`, and `fiches` rebuilt without a type `CHECK` (migration 0013, `kanevas-import-types`, AD-120); `fiche_alias`, `etiquettes` and `fiche_etiquettes`, and `recherche_fiches` rebuilt as `(titre, alias, sous_type)` (migration 0014, `kanevas-import-recherche`, AD-118); `fichiers`, `fichiers_sections` and `fiches.illustration_fichier_id` (migration 0015, `kanevas-import-mediatheque`, AD-117; `fichiers_attente`, created by the same migration, written by `assurerFichier` and sheet imports, `kanevas-import-fichiers`; the AD-93 illustration columns remain, unused); migration 0009 (`kanevas-import-markdown`) rebuilds `gabarits`, `scenarios` and `propositions` to raise their CHECK to 100,000 characters; numbers 0001 to 0007 are final, 0008 to 0016 are provisional until the epic merges into `main` and subsequent numbers are assigned at merge time (AD-51; `docs/donnees.md`). No SQL queries outside `src/services/` and `src/db/` (the stub seed, `src/bouchon/`, reads through `db.prepare` to find the identifiers it has just created).
- **Every route except `/healthz`, `/api/auth/*`, `/api/import/v1/*` (guarded by a Bearer token that ignores the cookie, AD-103) and, in stub mode, `/connexion-bouchon` is guarded by the session**; under `/api`, a
  missing session returns 401, elsewhere it redirects to login (AD-15).
- **Only one route calls a model: the assistant** (`src/routes/assistant.ts`, through `repondre`, AD-73), with the subscription
  token `CLAUDE_CODE_OAUTH_TOKEN`; the `services/llm/*` text transport is wired to nothing. No `ANTHROPIC_API_KEY` secret is deployed.
  The two routes (under the session guard, AD-15): `GET /api/univers/:id/assistant` returns `{disponible, catalogue: 'mj'|'joueur'}`;
  `POST /api/univers/:id/assistant/messages`, body `{message, historique: [{role: 'user'|'assistant', content}]}`, returns
  `{reponse, evenements: [{type, libelle, cible}]}`; an error returns `{message, code}` (codes from AD-75 and AD-77).
- OIDC client: `client_id` `kanevas`, callback
  `https://kanevas.berard.me/api/auth/oidc/callback`, issuer
  `https://auth.berard.me`. These values are shared with the client

## Decisions and rejected options

- **New repository, selective reuse from Antre-du-maitre (AD-10)**: Fastify
  bootstrap, OIDC, LLM transports, Dockerfile pattern and CI, without Prisma or the
  business domain. Rejected: forking Antre-du-maitre.
- **OIDC wired from the foundation**, rather than deferred: AD-10 includes it among what
  is reused in the foundation. `claude-token.ts` (admin setup-token window) was not reused in the
  foundation; it is reused by `kanevas-import-jeton-assistant` (AD-109, AD-112).
- **No canary page**: the frontend starts with the first business page (AD-57).
- **Public repository, MIT licence**: the public GHCR package avoids a pull-secret and
  Renovate auto-bump; MIT in the absence of a shared licence policy across the fleet.
  Reversed only if the code must become confidential.
- **Version read from `package.json`**: rejected, two unsynchronised sources.
- In the cluster (`tantive`; Authelia is on `homenode`) the pod runs as `runAsUser: 0` (the `games` apps' convention for
  a writable hostPath): the image's `node` user (uid 1000) is
  tolerated, not required. Under uid 1000 it would need a hostPath writable by that user.

## Components, and who talks to whom

```
browser (React, one SPA)  ──HTTP──▶  Fastify backend (one application)
                                         ├─ HTTP routes ─┐
                                         ├─ agent tools (GM | Player) ─┤─▶ service functions ─▶ SQLite + /data/attachments
                                         ├─ LLM provider (assistant)
                                         └─ codex exec (images), as a subprocess
Authelia (OIDC): identity only.

import script (outside the product, on Monsieur's Mac)
      ──HTTPS, Bearer──▶  /api/import/v1/univers/:id  (separate scope: token, never a cookie)
                                         └─▶ the same service functions (AD-2, AD-104)
```

- **Browser**: one React application (`react-router`, AD-16), served by the backend; it
  talks only to the backend, never to the database or disk. The assistant thread lives in the page
  (AD-28).
- **Fastify backend**: the only access point to data, disk, the LLM provider and
  Codex (AD-4). Every route is guarded by the session (AD-15): 401 under `/api`, redirection elsewhere; only `/healthz`,
  `/api/auth/*`, `/api/import/v1/*` (Bearer token, AD-103) and, in stub mode, `/connexion-bouchon` are public.
- **Service functions**: the sole implementation of each read and write, with its
  guards (`peutLireSection`, `peutEcrireSection`, `peutVoirFiche`, `fichierLisible` from `services/fichiers.ts`).
  Routes and agent tools call them in the same way (AD-2): this makes human / agent
  symmetry verifiable.
- **Agents**: two tool catalogues, GM and Player, selected on the server according to the
  account's role in the current universe (AD-26, AD-74), behind the `AgentTransport` port (AD-73).
- **Images**: a `GenerateurImage` port, `bouchon`, `aucun`, `codex` adapters (AD-88 to AD-90; AD-45, AD-50, AD-55).

## API d'import (`kanevas-import`, cible)

> Implemented: context and limits (`GET /`), batches, keyed sheets of every product type,
> file uploads and references, sheet deletion, campaigns, scenarios and relations. Sheet imports
> accept title, PJ, origin dates, keyed sections, aliases, labels, parent, subtype and illustration.
> `compte_rendu` additionally requires a known campaign key. Without `?lot=`, writes leave no batch trace.

**File import** (`kanevas-fichiers-put`): `assurerFichier` in `services/fichiers.ts` implements `PUT /fichiers/:cle` (same `{id, etat: creee|mise_a_jour|inchangee, avertissements}` result as sheets). Send `nom` (1–200 characters) and optional `visibilite` (`joueurs` by default, or `mj`) before the multipart `fichier`. SHA-256 is computed while `stockage.ts` streams the upload; unchanged bytes keep their disk token, changed bytes replace it. `dernier_import` protects the name and visibility independently; each protected field warns in the response and batch. An empty file is a 400 `invalide`, `champ: fichier`, counted as refused with its key and reason, without a stored file. `GET /` adds `limites.fichiersJointsParSection` (100). Files are counted under the batch’s `fichiers` nature.

**File references** (`kanevas-fichiers-references`): `PUT /fiches/:cle` takes `illustration` (image key; a document is a 400 `pas_une_image`), `fichiers` per section (at most 100 keys, else 400 `invalide`, `champ: fichiers`, counted as refused) and `fichier:cle:K` in a text. A known key is rewritten to `fichier:<id>`; an unknown one stays as sent, waits in `fichiers_attente` and warns the batch (never a refusal). When the file arrives (`PUT /fichiers/:cle`), one transaction rewrites the texts and sets the joins and the illustration, then deletes the waiting rows, without touching `version`, `version_importee` or `modifie_le`; a 101st join stays waiting with a warning. The replay compares after resolving known keys; the illustration and the joined files are protected by B-48 (keys in `dernier_import`). The batch closing counts the waiting references with the waiting links (E-18); the GM sees « Fichier en attente d’import » on E-9 (server-side view, AD-96: a reader never receives the key).

**Campaign and scenario imports** (`kanevas-reprise-suivi`, AD-121, migration 0016):
`services/import-suivi.ts` validates requests and counts outcomes through `noterDansLot`;
`assurerCampagne` and `assurerScenario` live beside the ordinary writes they call in
`services/campagnes.ts` and `services/scenarios.ts`. Campaign keys belong to the token's universe;
scenario keys belong to that campaign. `PUT` returns `{id, etat, avertissements}` like sheets.
Replay protects the campaign's name/status and the scenario's title/content separately; unchanged
scenarios keep their version and modification date. An unknown campaign is a counted 404
`campagne_inconnue`; an invalid body is a counted 400 `invalide` with `champ`; a closed batch is
409 `lot_clos`. `GET /` also exposes `nomCampagne: 80`, `titreScenario: 120` and
`contenuScenario: 100000` in `limites`. Scenario Markdown and origin-key links use the existing
reader in `scenarios.ts` (AD-97), resolving keys on read.

**Report and relation imports** (`kanevas-reprise-cr-relations`, AD-121):
`assurerFiche` creates reports through `creerCompteRendu`, without an author, reusing its initial
“Compte-rendu” section for the first imported section. Additional sections use ordinary section
services. A missing or unknown campaign is a counted 400 `invalide`, `champ: campagne`, before any
sheet write. Replay keeps the campaign and creation date, warning when either differs. E-13 uses
that creation date for both display and ordering, under the existing section visibility guard.
`assurerRelations` in `services/import-relations.ts` handles each array entry in its own transaction
through `relierSection`. The response is an array of `{section, cible, type, etat, avertissements}`
with `id` on creation and `code`/`raison` on refusal. States are `creee`, `inchangee`, `ignoree`
(unknown section or target, warning only) and `refusee`. Domain refusals `auto_relation` and
`limite_relations` also appear as `code` in the batch report. E-18 already displays the `relations`
counters; `GET /` exposes `relationsParSection: 100`.

Contrat que consomme le script de Monsieur, et tout autre (AD-103, AD-104). Base :
`https://kanevas.berard.me/api/import/v1/univers/:id`, en-tête `Authorization: Bearer kvs_…`. JSON,
noms en camelCase, dates ISO 8601. Une **clé d'origine** (`:cle`) : 1 à 200 caractères, sans `|`, `]`
ni saut de ligne, encodée dans l'adresse ; libre au script (`lieu:port-sel`, un identifiant Kanka…).
Une écriture porte `?lot=<id>` pour être comptée ; sans lot elle réussit mais rien n'est compté. Erreurs : la forme des routes (`{message, code}`) ; 401
`jeton_invalide` (corps unique) ; 404 univers autre ou clé inconnue (sauf `DELETE /fiches/:cle`, 204 même inconnue) ; 400 `invalide` avec `champ` ;
413 corps de plus de 8 Mio.

## Sécurité

| Menace | Réponse |
|---|---|
| Un joueur apprend qu'une chose existe (fiche, section, carte, titre) | Elle est absente partout ; son adresse répond comme une adresse inconnue (AD-22, AD-38). |
| Un fichier secret récupéré en devinant son adresse | Nom sur disque aléatoire ; aucune route statique ; garde revérifiée à chaque octet servi (AD-7, AD-35, AD-36). |
| L'agent comme porte dérobée | Mêmes fonctions et mêmes gardes que les routes (AD-2) ; catalogue choisi par le serveur (AD-26). |
| Un joueur écrit dans une section que l'agent du MJ lira (injection d'instructions) | L'agent du MJ peut modifier des sections : chaque écriture est listée dans le fil avec un lien (B-26), et une mise à jour du monde n'est jamais appliquée par l'agent (AD-48). **Risque accepté** en V1, pas de confirmation par écriture. Une proposition issue d'un compte-rendu qu'un joueur a écrit est lue par le MJ, côte à côte avec l'actuel, avant tout geste (AD-48, AD-81). |
| Une illustration reste dans le cache d'un navigateur après qu'il a perdu le droit de voir la fiche | **Risque accepté** (AD-93) : cache `private` du seul navigateur qui l'a déjà vue ; la fiche disparaît de ses listes, plus rien ne la redemande, et le serveur revérifie à chaque requête. *Depuis `kanevas-import`, l'illustration est un fichier de la médiathèque : le même risque vaut pour tout fichier dont la visibilité passe à « Réservé au MJ » (AD-111) ; elle n'est plus « jamais secrète ».* |
| Codex s'exécute sans bac à sable, dans un pod root ; son jeton est sur le volume sauvegardé | **Risque accepté** (décision de Monsieur sur le moteur) : le pod est le bac à sable, le jeton est en 0600, un processus par demande, un répertoire jetable. |
| *(kanevas-import)* Un jeton d'API volé (Mac, historique de terminal, dépôt du script) | Portée d'un univers, de l'API d'import seule, des droits d'un MJ ; expiration (30 jours par défaut) ; révocation par tout MJ ; base qui ne garde que l'empreinte ; « dernier usage » visible sur E-18 (AD-103). **Risque accepté** : pendant sa validité, le jeton écrit et supprime des fiches de l'univers comme le MJ. |
| *(kanevas-import)* Un fichier fermé à un joueur vu par une fiche, ou un fichier vu hors de ses droits | Double garde dans la vue par lecteur (conteneur et fichier), route de fichier gardée par sa visibilité, « Utilisé dans » réduit aux fiches lisibles (AD-111). **Risque accepté** (décision de Monsieur) : la mention « Image réservée au MJ. » / « Fichier réservé au MJ. » dit qu'un fichier est là ; un fichier ajouté depuis une fiche prend la visibilité de l'endroit d'ajout (bloc MJ ou section que les joueurs ne lisent pas tous : `mj`), ce qui ferme le cas d'un fichier ajouté au fil de l'écriture ; reste ouvert par la médiathèque un fichier `joueurs` **choisi** ensuite dans du seul contenu MJ (l'avertissement ne couvre que le sens inverse), ou envoyé `joueurs` par un import — le contrat d'API impose au script de marquer `mj` ce que la source n'utilise que dans du contenu MJ ; celui qui a ajouté un fichier le voit toujours (un joueur qui dépose un fichier dans sa section réservée le garde). Cache : celui d'AD-93, même risque accepté. |
| *(kanevas-import)* Du code qui s'exécute chez un lecteur, venu d'un texte ou d'un import (HTML, `javascript:`, image externe) | `html: false`, schémas de liens bornés, images et liens de fichier limités à la médiathèque de l'univers, rendu par une seule fonction serveur (AD-95, AD-111) ; une suite de vecteurs XSS dans les tests de cette fonction. |
| *(kanevas-import)* Un secret fuit hors de la fiche : recherche plein texte, lien, lien entrant, image, assistant, fil d'Ariane, arbre | Une seule vue par lecteur (AD-96) ; `contenu_public` pour l'index des non-MJ (AD-98, AD-101) ; deux gardes pour liens et liens entrants (AD-97, AD-100) ; ancêtre et enfant illisibles sautés (AD-99). Chaque voie a son critère dans `docs/ecrans.md`. |
| *(kanevas-import)* Un joueur efface un bloc MJ en réécrivant la section | Une section à bloc MJ ne s'écrit que par un MJ ; un non-MJ ne peut pas en écrire un (AD-98). |
| *(kanevas-import)* Un clic égaré supprime un univers | MJ seul, saisie exacte du nom ; la sauvegarde du volume reste le seul retour (AD-105). **Risque accepté** : tout MJ d'un univers peut le supprimer (les MJ sont égaux). |

## Organes et état

```
navigateur ──▶ Fastify ─┬─ cadre des modules (registre, activation, réglages, droits d'outil, import, routes communes)
                         │      └─▶ module `swn` : fonctions ─▶ tables swn_* (SQLite, même base)
                         ├─ routes `/api/univers/:id/outils/<module>/…` et `/api/systemes/:id/outils/<module>/…`
                         ├─ outils de l'assistant (neutres) composés par le catalogue d'un rôle
                         └─ fonctions de service du cœur (droits, sections, recherche) appelées par les modules
script de conversion (dépôt privé) ──jeton à portée d'outil──▶ API d'import étendue
```

L'état durable est en base (cœur + tables du module) ; sont **éphémères** : le cache des blocs générés de la carte (mémoire, perdu au
redémarrage sans dommage) et le calcul d'un trajet. Aucun état n'est dans le navigateur.

## Décisions

**AD-121 — Un module s'inscrit par une seule déclaration.** [ADOPTÉ, décision (e)]
Lie : tous les modules, B-57 à B-70. Empêche : un module qui s'accroche au routeur, à la barre, à l'assistant et à l'écran de réglages chacun à sa manière.
Règle : un module déclare, en un point unique, son nom, ses réglages communs (stockés sous le seul nom du module), les outils qu'il apporte (chacun : type, portée — un système de jeu ou tous —, dépendances, visibilité
par défaut, usages), ses réglages et leur forme, la forme de ses catalogues, ses routes, ses outils d'assistant et son point d'entrée d'interface (chargé à l'ouverture,
AD-133). Le cœur ne connaît aucun module par son nom. Un module regroupe un ou plusieurs outils (le module `swn` porte `galaxie` et `vaisseaux`, qui partagent le
réglage de portée de saut) ; l'activation et la visibilité se règlent **par outil**. *Rejeté* : un fichier de configuration par outil — les types de fiche n'en ont pas et
la déclaration doit se tester ; *un chargement à chaud de code tiers* — décision de Monsieur (5).

**AD-122 — Un contrat d'interface par type d'outil.** [ADOPTÉ, décision (3)]
Lie : B-59, B-66, B-71, B-75. Empêche : un générateur qui tient sa donnée à part, une carte qui écrit dans des sections.
Règle : trois types, chacun un contrat testé par un module d'essai : **carte dynamique** (rendue par son module dans la section Cartes, données à part ; le module liste ses cartes — titre, visibilité — et E-10 les ajoute à celles de `cartes`, dont les formes ne changent pas), **générateur** (le
résultat est une section gérée d'une fiche, les choix de construction sont les données de l'outil rattachées à la fiche, avec la version des règles et des réglages), **aide
de jeu** (ses données et son entrée ; aucune dans cette epic). Chaque contrat dit comment il traite un réglage qui change (AD-128). Un type est ajouté quand un deuxième
besoin ressemble au premier, pas avant. *Rejeté* : un moteur générique unique — il aurait les abstractions de SWN (décision (1)).

**AD-123 — Les données d'un outil sont en base, dans les tables de son module, à deux niveaux.** [ADOPTÉ, décisions (4), (d), point 6]
Lie : tout module. Empêche : un fichier ou une table JSON générique qui perd liens et requêtes ; un accès hors du module.
Règle : tables préfixées, créées par les migrations du module, une ligne rattachée à un univers (ou à un système pour son catalogue), les références de fiche par identifiant,
aucun SQL hors des fonctions du module ; le rangement (tables typées, documents à forme déclarée, ou les deux) est le choix du module. Le niveau **système** (le jeu) et le niveau
**univers** (la campagne) : un univers voit les deux, une donnée d'univers de même clé remplace celle du système, et un **retrait** d'univers (une clé du système
marquée absente pour cet univers) l'efface de sa vue sans toucher au système. Un catalogue de système n'a aucun élément caché ; un élément d'univers porte
`masque` (MJ seul), posé et ôté par un MJ de l'univers, et la lecture le filtre pour un joueur comme un système secret (B-62, décision de Monsieur du 2026-10-17).
La résolution se fait **par clé, une fois** : l'élément d'univers s'il existe (masqué ou non), sinon celui du système s'il n'est pas retiré ; un remplacement masqué
ne laisse jamais reparaître l'élément du système, et le calcul n'emploie que l'élément résolu.
*Rejeté* : masquer un élément du système (le système est le jeu, commun à ses univers : pour qu'il n'existe pas dans une campagne, on le retire). Le contrat impose : clé, version, rattachement, forme déclarée
et vérifiée à l'import. *Rejeté* : fichiers sur le volume ; table générique JSON.

**AD-124 — Un cadre d'API commun, des routes propres à chaque module.** [ADOPTÉ, décision (e)]
Lie : B-58, B-65, B-61. Empêche : des conventions d'erreur et d'activation différentes par module.
Règle : les routes d'un module vivent sous `/api/univers/:id/outils/<module>/…` et `/api/systemes/:id/outils/<module>/…` ; l'**activation est vérifiée à l'entrée** (outil
désactivé ou invisible pour le rôle = adresse inconnue, même réponse qu'une route absente) ; mêmes identités (session pour l'écran, jeton à portée d'outil pour les scripts), mêmes
conventions (erreur `code` + champ, pagination, version contre l'écriture concurrente, mise à jour par clé) ; le module reçoit l'acteur, son rôle et le mode joueur. Deux routes
sont communes à tout module : la **description** de l'outil (réglages et leur forme, dépendances, activation : E-20 la lit) et l'**import d'un catalogue** (aperçu puis application,
rapport ajouté / modifié / refusé). Écran, API et assistant passent par les **mêmes fonctions** du module (routes minces, AD-2).

**AD-125 — Activation, visibilité et réglages se résolvent système → univers.** [ADOPTÉ, décisions (6), point 3, point 10]
Lie : B-57 à B-60. Empêche : trois lieux pour décider qui voit un outil, et des réglages lus à des endroits différents.
Règle : une seule fonction résout, pour (univers, outil), l'état *activé*, la visibilité par rôle et la valeur de chaque réglage : la ligne d'univers s'il y en a une, sinon celle du système,
sinon le défaut déclaré. Le **responsable** du système (créateur par défaut, rôle transmissible) est le seul à écrire au niveau du système ; tout MJ écrit au niveau de son univers ; l'admin
d'instance n'a aucun accès. Désactiver au système cache l'outil aux univers qui le suivent ; un univers qui l'a forcé garde l'accès, données du système comprises. *Rejeté* : « tout MJ d'un univers
rattaché règle le système » (le geste touche tous les univers) ; *l'admin d'instance responsable* — il n'a pas accès au contenu (AD-9). Les gabarits gardent leur règle actuelle.

**AD-126 — Les droits d'un outil sont à deux niveaux, appliqués dans les services.** [ADOPTÉ, décision point 3]
Lie : B-59, B-73. Empêche : un outil qui laisse fuir un secret en vue joueur (recherche, route, zone, menu).
Règle : (1) le cœur décide si l'outil est **visible** (activé, visible pour le rôle) ; hors de là il est introuvable. (2) L'outil déclare ses **usages** et applique ses droits internes jusqu'à la ligne,
avec les fonctions de droits de Kanevas et leur vocabulaire (MJ seul, joueurs, auteur, mode Joueur). « Ce que le compte ne peut pas lire n'existe pas pour lui » vaut pour la carte (élément par élément),
la recherche, les trajets, la génération des blocs (AD-132), l'assistant et les liens. L'acteur n'a jamais plus de droits que le compte ; le mode Joueur d'un MJ le ramène à ceux d'un joueur.

**AD-127 — Une section « gérée par un outil » est un verrou sur le contenu, distinct de l'auteur.** [ADOPTÉ, décisions (g), (h), (i), (j)]
Lie : B-66, B-67, B-74, B-77. Empêche : deux écrivains d'une même section ; un joueur qui écrit plus que ses droits ; une section illisible sans l'outil.
Règle : la section porte `gere_par` ; seule la fonction d'écriture de cet outil, qui **passe par le chemin d'écriture de section existant** (`ecrireContenu`, avec version lue ; AD-48), change son contenu ;
l'éditeur et l'API des sections la refusent à tout autre. L'outil vérifie l'usage et le rôle d'auteur du compte (« l'auteur écrit ») et écrit **au nom du compte**. Chaque section d'outil a un **contenu structuré**
au format déclaré, un composant d'affichage fourni par le module (chargé seulement quand une fiche en contient une), et une **version texte (Markdown) obligatoire**, produite avec le contenu et mise dans
`contenu` : c'est elle que lisent la recherche, l'assistant, l'export, et la fiche quand l'outil est désactivé. Mêmes interrupteurs d'audience que toute section. Kanevas n'a pas de propriétaire de fiche :
l'auteur est par section. *Rejeté* : la fiche comme unité générée (la fiche mêle sections gérées et libres).

**AD-128 — Un changement de source ne réécrit rien en silence.** [ADOPTÉ, décision (7)]
Lie : B-67, tout générateur. Empêche : un vaisseau dont les chiffres changent sous le joueur après un réglage.
Règle : un résultat calculé garde la version du catalogue et des réglages qui l'ont produit ; quand ils diffèrent des courants, il est dit **périmé** (état calculé à la lecture, jamais stocké) et se
recalcule sur un geste explicite, ou sur proposition (même mécanique que la proposition de mise à jour, AD-79), selon ce que l'outil déclare. Un tour validé (plus tard) est figé.

**AD-129 — Une donnée d'outil modifiable est protégée comme une section.** [ADOPTÉ, décision point 11]
Lie : B-64. Empêche : un écrasement muet entre deux MJ.
Règle : toute donnée d'outil modifiable porte `version` ; l'écriture donne la version lue ; une version périmée est refusée avec la même réponse qu'une section (`conflit`, code `donnee_modifiee`), l'écran
dit et offre de recharger. Une section gérée est déjà protégée. Pas de verrou ni d'édition en direct.

**AD-130 — Un catalogue est un fichier JSON de transport, la base le stocke.** [ADOPTÉ, décision (b)]
Lie : B-61, B-65, B-79. Empêche : un import qui écrase, qui duplique ou qui supprime sans le dire.
Règle : un fichier par module, une section par nature d'élément, chaque élément une **clé** ; le fichier est vérifié par le schéma du module **avant** d'être appliqué (élément fautif refusé avec son champ, le
reste passe) ; réimport = mise à jour par clé sans doublon ; un élément retiré du fichier n'est pas supprimé ; le catalogue a une version, qu'un résultat garde (AD-128). Deux voies, mêmes fonctions : l'onglet « Outils »
(aperçu puis application) et l'API d'import étendue avec un jeton **à portée d'outil** (rapport de lot par nature). Comme B-48, un import n'écrase pas ce qu'un humain a modifié dans Kanevas depuis. Un jeton est celui d'un univers : il n'écrit le catalogue **du système** que si son compte en est le responsable à cet instant (le rôle se relit à chaque usage, comme le rôle MJ d'un jeton d'import).

**AD-131 — Rien d'Éneria n'entre dans le dépôt public, tests compris.** [ADOPTÉ, lettre de mandat]
Lie : B-78, B-79. Empêche : un catalogue du livre, une fiche de règles traduite, une valeur calculée sur les données réelles, une capture, dans `kanevas` ou ses journaux publics.
Règle : le dépôt public ne contient que le **format**, le code qui le lit et un petit catalogue d'essai **inventé** (avec ses propres valeurs attendues, calculées à la main ou par les règles du module) ; la suite
attestée et la CI de `kanevas` tournent sur ces données synthétiques seules (décision de Monsieur, 2026-10-16). Les tests sur données réelles, leurs valeurs de référence (calculées une fois avec les outils actuels de Monsieur, figées) et le script de conversion vivent dans `AntorFr/eneria`, dossier
`_outils/kanevas/`, et se jouent **dans les pods**, qui lisent `eneria` avec l'accès qu'ils ont : ils exercent le code de `kanevas` à une révision épinglée, hors de la suite attestée. Un écart est un bug du portage ou une correction de règle décidée et notée. *Rejeté* : un workflow « tests » de `kanevas` avec un secret du dépôt privé — décision de Monsieur du 2026-10-16 : la CI est publique, ses journaux aussi ; *des données réelles anonymisées* — la valeur du test est dans la donnée exacte.

**AD-132 — La carte est infinie : les systèmes anonymes se calculent, côté serveur, par blocs.** [ADOPTÉ, point 9]
Lie : B-71, B-73. Empêche : un client qui reçoit toute la carte ; un territoire secret qu'on devine à la densité générée.
Règle : un bloc de 5×5 hexagones se génère à partir des coordonnées et d'une graine (même emplacement, même résultat, testé) **côté serveur**, sous les droits de l'appelant : la densité tient compte
des seuls territoires que ce compte lit ; le résultat se met en cache (mémoire). Sont stockés seulement les systèmes définis, les routes, les zones et les systèmes anonymes **promus** (qui gardent leur emplacement et deviennent
des données de l'univers avec leurs droits). La **graine** (propre à chaque galaxie, protégée) : la changer exige une confirmation qui dit que tous les systèmes non définis changent de place. La vue ne reçoit que les blocs qu'elle montre. *Hors périmètre* : la carte hors connexion.
[À VÉRIFIER] : le cache d'un bloc dépend des territoires lisibles par l'appelant — la clé de cache doit porter le niveau de lecture (MJ / joueur / mode Joueur) ; vérifier à la conception de la tranche.

**AD-133 — Le code d'un outil se charge à son usage.** [ADOPTÉ, point 9]
Lie : B-70. Empêche : un bundle qui embarque la carte et le concepteur pour tous les comptes ; un data.js envoyé en bloc.
Règle : le point d'entrée d'un module et le composant d'une section sont chargés par un import dynamique, à l'ouverture de l'écran ou quand une fiche contient la section ; un compte sans accès ne le charge jamais ; les données
suivent la vue (AD-132). Un composant respecte l'existant (tokens de `frontend/src/ui/tokens.css`, `docs/charte.md`) et se joue à 360 px de large. Critère de recette de chaque outil : téléphone et tablette.

**AD-134 — Un lien partageable mène à une ressource stockée.** [ADOPTÉ, point 8]
Lie : B-68. Empêche : un contenu encodé dans l'adresse qui contourne les droits et la version du catalogue.
Règle : l'adresse d'un système de la carte ou d'une fiche de vaisseau est un identifiant stocké ; elle se lit selon les droits de qui l'ouvre (illisible = introuvable). Aucun contenu n'est encodé dans l'adresse.
L'impression est une fonction ultérieure du cœur pour toute fiche (hors epic).

**AD-135 — Désactiver cache, supprimer est un geste à part.** [ADOPTÉ, point 6]
Lie : B-63. Empêche : une donnée perdue par un clic sur une bascule.
Règle : désactiver un outil ne touche aucune ligne ; il cache l'entrée, les adresses, les données et la vue des données du système pour l'univers ; ses sections gérées restent lisibles en version texte avec un bandeau
« outil désactivé », sans régénération ni modification. Supprimer des données est une fonction à part, réservée (responsable pour le système, MJ pour l'univers), dont la confirmation compte ce qui part et, pour le système,
ce qui s'en sert encore (univers, éléments locaux, conceptions). Supprimer un univers efface les données de ses outils (une transaction, tables du module comprises).

**AD-136 — Les capacités d'un outil à l'assistant sont des outils neutres du module.** [ADOPTÉ, modèle (8)]
Lie : B-69. Empêche : un assistant plus permissif que l'écran ; un outil visible pour un rôle qui ne l'a pas.
Règle : un module déclare des outils d'assistant de la forme de `catalogue` (`{nom, description, schéma, executer}`), qui ne composent que des fonctions du module (AD-27) ; `catalogueDe` les ajoute quand l'outil est activé et visible
pour le rôle lu en base ; compte, univers et rôle sont fermés, jamais un paramètre ; un refus revient `{ok:false}` sans événement.

**AD-137 — Deux modules se parlent par leurs fonctions, sur une dépendance déclarée.** [ADOPTÉ, décision (e)]
Lie : tout module. Empêche : un module qui lit les tables d'un autre ou l'appelle par HTTP.
Règle : une dépendance se déclare dans la déclaration (AD-121), l'écran d'activation la fait respecter (B-58) ; l'appel se fait par la fonction exportée de l'autre module, sous les mêmes droits. Dans cette epic, aucune dépendance entre outils n'existe : `vaisseaux` lit la portée de saut réglée au niveau du module `swn`, pas la carte. Le mécanisme se teste avec le module d'essai.

## Interfaces

Conventions de `kanevas-import` conservées (erreurs `code` + champ, pagination, version). Les identifiants d'élément de catalogue sont des **clés** stables en texte, jamais l'identifiant de ligne. Les dates en ISO 8601 UTC. Un réglage a une
forme déclarée avec un schéma (zod côté serveur).

## Déploiement et exploitation

Aucun nouveau service, secret ni volume. Les migrations du module s'appliquent au démarrage par l'exécuteur existant (AD-14). L'image publiée par la CI (tag semver) est épinglée dans `k8s-home-lab` par une PR préparée, que Monsieur fusionne.
On sait que ça marche par `/healthz` (version) et la recette en bouchon. Sauvegarde : la base existante porte tout ; les données d'un outil en font partie.

## Sécurité

La menace : un secret de MJ (système fantôme, route privée, territoire, conception cachée) qui arrive à un joueur par la carte, la recherche, un trajet, la densité générée, un lien, l'API ou l'assistant. Contre :
droits élément par élément dans les fonctions du module (AD-126), génération côté serveur sous droits (AD-132), outil invisible = introuvable (AD-124), jeton à portée d'outil, section gérée verrouillée (AD-127). Aucun secret d'Éneria dans le dépôt public ni ses journaux (AD-131).

## Bouchons

Aucune dépendance nouvelle qui exige un jeton, un compte ou une authentification : les modules ne font aucun appel externe. L'assistant garde son bouchon (`KANEVAS_STUB=1`, AD-78), dont le script peut appeler les outils d'assistant des modules.
La recette se joue en bouchon, sur le catalogue d'essai inventé.
