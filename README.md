# kanevas

RPG management system (lore, campaigns, session reports, permissions, maps).
This repository provides the foundation (health, OIDC, image, CI) and the **first business feature**:
a GM creates a universe, gathers its players and writes sheets whose sections each have
their own audience; a player reads only what that audience allows. What the product enables and
through which screens: `docs/parcours.md`, `docs/ecrans.md`, `docs/donnees.md`. Beyond the first business feature, the repository includes the **game system**: a reference collection (rules, creatures, items) shared by several
universes and linked from the universe settings. It also includes (epic `kanevas-fiches-liees`, on `main`) **relations with a nature and qualifier**, **search by link** (advanced E-17), the **« gone » mark** and the **Famille** type and the **« Fiches liées » block** of a sheet (E-9). It also includes **session tracking**: adventures (campaigns and scenarios, sheets of type « Aventure » with a status), their « Préparation » block in five categories (GM) and their « Comptes-rendus » block (any member). The universe's **media library** (E-19) stores each image or document as a row in `fichiers` with its own visibility (player-visible or GM-only), determined by where it is added; a section attaches it (up to 100) or embeds it in its text, and a sheet can use it as its illustration. It includes **instance administration**: an account in the Authelia `parents` group sees universes and their members (never their content) and repairs them (E-5, B-6). Each sheet can have an **illustration** (an image from the media library, set by the GM, in the E-8 card grid and E-9 header), and **game systems** have their screen outside universes (E-16, E-15). It also includes **relations** between sheets (the sheet's « Relations » block) and **search** across all sheet types, by alias and label (E-17), **maps** (E-10, E-11: illustrated map with background and tokens, or relation graph; visible to players or hidden; E-3's « Cartes visibles » block) and each member's **assistant** (E-12: a conversation panel that searches, reads, writes and, for the GM, **proposes a section update** from a session report, written only by their « Appliquer » action, with exactly that person's permissions; model access uses the operator's Claude subscription, `CLAUDE_CODE_OAUTH_TOKEN` or, without redeployment, the token the instance admin sets from administration; in stub mode, a script responds). The GM can also request a **portrait**: the assistant generates an image and attaches it to the section, where it enters the media library (Codex engine using the operator's subscription; in stub mode, a fixed image).

The sheet type list comes from the server; the frontend holds only the icon → component table, in `frontend/src/types-contexte.tsx` (where a new type's icon is added).
A screen is a `frontend/src/ecrans/<nom>.tsx` file registered by the registry
(`frontend/src/registre.ts`); frontend colours come only from `frontend/src/ui/tokens.css` (the sole exception is the stub banner on server-rendered pages, `src/routes/pages.ts`)
(`docs/charte.md`). The shell (`Cadre.tsx`, `Barre.tsx`: icon navigation, top bar, phone drawer,
avatar menu with theme and sign-out) and shared components (`frontend/src/ui/`: button, menu, toast,
dialog, switch, badge…) are common to all screens. Fonts (Fraunces, Newsreader, Inter,
`@fontsource`) and icons (`lucide-react`) are bundled, with no request to a third-party host (AD-92).

The brand (the « Marge » icon, `assets/brand/kanevas-marge/`) reaches the browser as seven public files of `frontend/public/` (favicon, apple-touch-icon, 192/512/maskable icons, `site.webmanifest`), served without a session (AD-135) and shown in the tab, the sidebar outside a universe, and at install. The installed app still needs the network (no service worker).

To **see the brand**: after `npm run build` (re-run it after any change under `frontend/public/`, the server serves `dist/public`), start the stub mode (`KANEVAS_STUB=1 npm start`), open `http://localhost:3001/`, choose an account on the stub sign-in page, then look at the tab and at the sidebar on « Mes univers » (the brand shows outside a universe only). `curl -sI http://localhost:3001/site.webmanifest` answers 200 without a cookie. To check the install manifest, open the browser's developer tools, Application ▸ Manifest. The sign-in page itself is Authelia's in production and the server's stub page in stub mode: it declares no brand (the browser may still show the icon in its tab, `/favicon.ico` being public). Also check both themes (avatar menu ▸ Clair / Sombre) and that inside a universe the sidebar shows the selector, not the brand.

Docs: `npm run controle-langue -- --links README.md docs/*.md ARCHITECTURE.md` counts the French words left outside « … » quotations and code blocks (only nine function words, « le, la, les, des, est, pour, avec, une, dans », so a zero is not proof that no French is left) and the facts (B-n/P-n/E-n/AD-n, headings, code blocks, table rows) that differ from the reference, per `##` section. The reference is the frozen state of the docs before translation, named by `scripts/controle-langue.base` (one bare commit hash, which must exist in the clone): the check shows that the translation kept every fact, so a section, heading or table row added after that commit, as new text written in English is, shows up as a difference and is not a defect. Code (backtick) spans are counted like prose; external links are ignored, and a link already broken in the reference is not reported. For `docs/ecrans.md` the script also hard-codes the product changes made between the reference and the translation (`referenceSections`, `referenceAmendment`, `PRODUCT_EVOLUTION`): the script's comments and constants number the sections of the frozen reference, shifted by one after section 14, whereas the output and `--headings` number the current text (the shift starts at the section titled `kanevas-images`): always pick a `--sections` range from `--headings`, not from the script's comments. `--base <ref>` replaces it and `--sections <file>:<i>-<j>` limits the check to sections i to j (section 0 is what precedes the first `##`). The output is JSON: `files`, each with `file`, `french` (total), `facts` (`identifiers`, `headings`, `blocks`, `tableRows`) and `sections` (`number`, `title`, `french`, `words`, `facts`, `differences`; each difference has `fact`, `before` (the reference, or the expected value with `--expected`) and `after` (the current text, or the measured value); `differences` also sits at file level, and in each Release; with `--links`, `links` lists the relative links and anchors that no longer resolve (`section`, `link`). Without file arguments the script checks `README.md`, `docs/*.md` and `ARCHITECTURE.md` (run from the repository root); `--sections` adds its file. Exit code 0 = clean; 1 = something to fix (a French word left, a difference, or a broken link: check `french`, `differences` and `links`); 2 = invalid invocation or unavailable input (unknown ref, `gh` missing). Two other modes do not compare to the reference: `--headings <file>` lists the number and title of each `##` section (to pick a `--sections` range), and `--releases` checks the body of every published GitHub Release instead of files (it needs the `gh` CLI, authenticated, and network access; it takes no file, `--links`, `--headings` or `--base`). In that mode the output has `releases`, each with a `tag`, the `french` count and `counts` (`headings`, `bullets`, `links`, as numbers), and `--expected tag:headings=n,bullets=n,links=n` (only with `--releases`, repeatable) compares them with the counts noted before the edit. New text is written in English directly. Code-block contents (command comments, the tree above) are exempt from the count.

Tests without Docker: `npm ci` first (an existing `node_modules/` may be incomplete; if `npm ci` fails with `ENOTEMPTY`, rerun it, or `rm -rf node_modules` beforehand), then `npm run build:wasm` (Rust, see « Rust / WebAssembly »), `npm run typecheck` then `npm test` (they also run the e2e tests, which fail if Playwright is missing, which takes time: see “End-to-end tests”; a single file, e2e or otherwise (`src/db/migration-types.test.ts`: less than a second): `node --import tsx --test <fichier>.test.ts`, and, when launched by hand, never two suites at once (`npm run tests:attestes` sets its own concurrency), since e2e tests start their servers and fail en masse under concurrency; after renumbering a migration, `rm -rf dist` before `npm run build`, otherwise the old copied file stays in `dist/db/migrations` and the server no longer starts); the reference Docker path is in `CLAUDE.md`.

## Local startup

To **view the screens**, use the command under “Without Authelia: stub mode” below (`npm ci && npm run build:wasm && npm run build && KANEVAS_STUB=1 npm start`; `npm run build` fails without `rust/pkg`; `build:wasm` needs Rust, see « Rust / WebAssembly » — the Docker block below has none, so it cannot build the screens). The block below only serves the API (`/healthz`). `npm run build` writes to the repository's `dist/`: after renumbering a migration, run `rm -rf dist` first.

```bash
# writes node_modules/ and ./data/ (database and session.key) into the mounted repository, as root; both are ignored by git.
# Without a prior `npm run build` (done on the host, outside this command), this route serves only the API: see below.
# To see the screens: the Node container alone has no Rust, so no `npm run build:wasm` nor `npm run build`; use the command of the “stub mode” section on a host with Rust.
docker run --rm -p 3001:3001 -v "$PWD":/src -w /src node:20-bookworm-slim sh -c "npm ci && npm run dev"
# then, from the host: curl http://localhost:3001/healthz
# (this image has no Rust: the API starts and answers /healthz, but the galaxy's block reads answer their generic server error until `npm run build:wasm` has run on a host that has Rust)
# (without KANEVAS_STUB=1 or the four OIDC_*, `/` leads to an OIDC sign-in that answers 404: no screen; to see them, start the stub mode above)
```

This block does not create a `.env`: defaults suffice for `/healthz`; OIDC
stays disabled (`/api/auth/oidc/login` returns 404). To enable it, create `.env` (see
`.env.example`) at the root: the `-v "$PWD":/src` mount makes it readable. This block also creates
`node_modules/` in the host repository (ignored by git); it belongs to root: remove it with
`docker run --rm -v "$PWD":/src -w /src node:20-bookworm-slim rm -rf node_modules` or `sudo rm -rf node_modules`.

Or, with Node 20+ installed locally (`engines`: `>=20`; the suite also passes on Node 22, the Docker image is Node 20, no workflow plays the suite; `better-sqlite3` stays on `^12` because 13 requires Node ≥ 22):

```bash
npm ci   # not `npm install`; run it to the end, also on a clone that already has a node_modules/
cp .env.example .env
npm run dev            # or, without reload: npm run build && npm start (`npm start` alone fails without `dist/`, ignored by git)
curl http://localhost:3001/healthz   # -> "kanevas 0.0.0-dev"; the galaxy needs `npm run build:wasm` first (see « Rust / WebAssembly »)
```

This block serves `/healthz` and the API only; to log in and see the screens, use the stub-mode command under “Without Authelia: stub mode” (`KANEVAS_STUB=1`).

`npm run dev` serves the API, and the frontend only if it has been built: first run
`npm run build` (it builds `dist/public`, served by Fastify behind the session; without it, `/`
shows no screen). `npm run dev:front` starts Vite alone (port 5173 by default) and proxies only
`/api` to `http://localhost:3001` (hardcoded in `frontend/vite.config.ts`: change it if `PORT` changes): it does not replace the server for stub sign-in. To use it, first start the
stub server (port 3001), sign in at `http://localhost:3001/`, then open
`http://localhost:5173/` (the session cookie does not depend on the port).

The Node 20 container of `CLAUDE.md` has no Rust: it runs the commands that do not need the Wasm only; the pods that attest carry Rust and play `npm ci && npm run build:wasm && …` on the host. Without Docker, a recent local Node
suffices for the same commands (`npm ci && npm run build:wasm && npm run typecheck && npm test`).

### Levels of tests

`.sdlc.yaml` declares, under `tests:`, three more keys that are not levels: `installation: npm ci && npm run build:wasm` (what needs the network or a toolchain and not the code under test, played once per extraction by the chain; a failure there keeps the npm or cargo error on its output and is a transient outage, not a red run), `fichiers: node scripts/rejouer-tests.mjs --fichiers {tests}` (prints `name<TAB>file` for each named test, plays and builds nothing, needs no `npm ci`; a name no file declares is named on stderr and the exit is 1) and `outillage: [package.json, scripts/]` (what the chain takes from `origin/main`; `src/scripts-tests/sdlc-niveaux-declares.test.ts` fails if a path does not exist or a script the declared commands run is under none). `ecrans:` and `rejouer:` no longer start with `npm ci` and pass `--installe` after their argument, which skips only the `build:wasm` step (`installation:` did it); without the flag the scripts behave as before. It declares five levels of tests (listed in the table in no order of duration) and, beside `ecrans:`, `ecrans_liste:`: not a level (`attester` never plays it) but the command that lists the screen tests `ecrans:` would play; the table puts it after `ecrans:`. `attester` picks the level a branch owes: a `feature/<id>` branch of the chain's store plays `fiche`, any other branch plays the whole suite (`--base` and `--cible` name the base and target explicitly; it also writes `rapport-tests.json` at the root, exit codes 0, 1, 2, 3). `{tests}` is the list of test names to replay (`describe > test`, separated by `|` or line ends); `{base}` is the commit the change is measured from (`git diff --name-only {base} HEAD`): by hand, pass the merge-base with `main` (`$(git merge-base origin/main HEAD)`, or `main` when the clone has no `origin`); a base that is no commit of the checkout exits 2.

| Level | Command | What it plays | Measured (2026-11-16, 18-CPU pod) |


### End-to-end tests

`npm test` also runs `src/e2e/`: `node dist/server.js` in stub mode, driven by real Chromium through
Playwright. The harness (`ensureBuilt`) reruns `npm run build` when `dist/` is missing or when a source
(`src/`, `frontend/src/`, `frontend/index.html`, `package.json`, `tsconfig.json`, `frontend/tsconfig.json`, `frontend/vite.config.ts`) is newer than `dist/server.js` or `dist/public/index.html` (AD-harnais-5).
Text in `docs/ecrans.md` uses the straight apostrophe; the interface uses the typographic apostrophe (’).
Playwright is not a repository dependency: it must be installed globally
(`/usr/lib/node_modules` or `/usr/local/lib/node_modules`) or in the current directory (`npm install --no-save playwright@1.63.0`) with Chromium, which
`node:20-bookworm-slim` does not do; `npm run tests:attestes` installs it locally (`--no-save`) when it sees none, so the suite plays the e2e tests. To check whether it is found: `ls /usr/lib/node_modules/playwright` (this only proves the package: install Chromium too with `npx playwright install --with-deps chromium`; it may live under `PLAYWRIGHT_BROWSERS_PATH`). Where it is missing, the harness throws at import: every e2e file **fails** and the suite exits non-zero, it no longer skips them (AD-harnais-4);
the other tests (services, HTTP routes) run everywhere. `HARNAIS_RACINES_PLAYWRIGHT` (resolution roots separated by `:`, an empty value means none) replaces the list (current directory, `/usr/lib/node_modules`, `/usr/local/lib/node_modules`) where the harness looks for Playwright; `harnais-garde-fous.test.ts` uses it to prove the failure. Every e2e server is ready once `/healthz` answers 200 (`attendreServeurPret`, `src/e2e/harnais.test.ts`, used by `startServer` and by the test files that spawn their own server): the wait stops as soon as the server exits and fails after 30 s without any CPU time consumed by the server (a starved server that still progresses keeps going, ceiling 180 s); the failure message ("server did not start") gives the elapsed time and the tail of the server's output. A server that dies in the middle of a test file fails the running test at once (`avecServeur`), with "server died (signal SIGKILL)" or its exit code and the tail of its output, instead of a mute page timeout. Durations vary with the machine (about 28 minutes for `src/e2e` in a pod; no workflow plays them). Allow about ten minutes without e2e tests and thirty with Playwright; a full `npm run tests:attestes` (typecheck, build and every test, two files at a time) took about 36 minutes on a 12-CPU pod, and a run silent for much longer than that is stuck. `npm run tests:attestes` writes one TAP line per test to `resultats.tap` (the totals and the status are `attester`'s, in `rapport-tests.json`); a missing Playwright fails the e2e files.
Screen tests prove what the user sees, not what a route or a service guarantees (« the effect through its door, the display on screen »): every test of `src/e2e/` is classed in `docs/tests-ecran/lot-*.md`, and `src/scripts-tests/inventaire-ecrans.test.ts` fails when a screen file or one of its tests has no line there, or when an « effet » line names a door (an out-of-screen test) that does not exist. Duration of the screen suite, measured by `npm run tests:attestes` with two files at a time on a 13th Gen Intel Core i5-13500 (18 logical CPUs, pod), summed over the screen files (`node scripts/duree-tests-ecran.mjs resultats.tap`): **before 4 904.5 s (81.7 min, 275 files)**, **after 3 651.0 s (60.9 min, 256 files)**, 19 files removed because their tests moved to their doors (listed one by one in `docs/tests-ecran/apres.md`); the 256 files left went from 4 518.3 s to 3 651.0 s. The method, the inventories and both measures are in `docs/tests-ecran/` (`README.md`, `lot-*.md`, `avant.md`, `apres.md`).
An e2e test must wait for the state it reads (an element appearing or disappearing, navigation completing), never a fixed delay (`waitForTimeout` is banned by `src/e2e/harnais-sans-delai.test.ts`; `attendre(page)` waits for in-flight requests, loading signs and a quiet DOM, helpers `attendreVisible`, `attendreAbsent`, `attendreTexte`, `attendreTransitions`; AD-harnais-n are the decisions of ARCHITECTURE.md « kanevas-harnais-preuve »): under load, a test that reads the DOM too early fails at random. To reproduce a 4-core run (4 cores, two files at a time), run from the repository root (about 28 minutes for `src/e2e` in a pod), after `npm run build` (`ensureBuilt` rebuilds a stale `dist/` by itself, but needs `rust/pkg/` from `npm run build:wasm`) and without rerunning typecheck or build: `taskset -c 0-3 node --import tsx --test --test-concurrency=2 $(find src/e2e -name '*.test.ts')`. If an e2e test times out under heavy load (8 s in files that set it, Playwright's default of 30 s elsewhere), rerun it alone (`node --import tsx --test src/e2e/<fichier>.test.ts`) before treating it as a defect.

## Rust / WebAssembly

Rust is compiled to WebAssembly (Wasm) once and the same `.wasm` runs in the browser and on the Node server (AD-rust-1 to 10, `ARCHITECTURE.md`). The ground ships the example module `rust/modules/exemple` (`fnv1a(text)`, `version()`); the first product function is the `generation` module of the core, crate `rust/modules/coeur` (its second module, `rendu`, draws a body from its aspect: `dessiner_astre(aspect_json, cote, version_rendu)`, `version_rendu`, `catalogue_aspects`; `generation` also has `tirer_systeme`, `transition_defaut`, `orbite_heure_vers_plan`, `plan_vers_orbite_heure`, `heure_vers_voisin`; `tirer_bloc`, `hex_vers_plan`, `plan_vers_hex`, `densite_defaut`, `AD-etoiles-1` to `7`): it draws the stars of the galaxy (E-21) at the places of Éneria's generator, for the server (`src/services/swn/tirage-etoiles.ts`, the only caller) and the browser (`frontend/src/wasm/coeur.ts`). Its fixtures (`rust/modules/coeur/tests/fixtures/`) come from Éneria's generator on a neutral seed and make the rule; `cargo test` and `src/wasm/coeur.test.ts` replay them. If the server cannot load `coeur`, a block request answers the generic server error, with no fallback to another draw. **Since this slice, every command that builds, typechecks or runs the app (`npm run typecheck`, `npm run build`, `npm test`, the stub-mode command above; not `npm run dev`, which does not load the module) needs `npm run build:wasm` first**, on a host that has Rust: the Node-only Docker routes of this README cannot run it. It needs `rustup`, `rustc`/`cargo` 1.99.1 (pinned by `rust/rust-toolchain.toml`), the `wasm32-unknown-unknown` target (`rustup target add wasm32-unknown-unknown`) and `wasm-bindgen` at the exact version of `rust/Cargo.lock`, now 0.2.130 (`cargo install --locked --version =0.2.130 wasm-bindgen-cli`) in the PATH; the script names a missing tool and installs nothing (the first `cargo install` of `wasm-bindgen-cli` compiles for minutes; `rustup`, `cargo install` and `--locked` fetch from the network: an offline host cannot build; `rust/pkg/` and `rust/target/` are git-ignored; the chain's pods already carry all of it). `npm run tests:attestes` plays `build:wasm` itself.

```bash

npm run build           # copies rust/pkg to dist/wasm/ (does not compile Rust; fails telling you to run build:wasm)
cd rust && cargo test --workspace --locked   # the Rust tests; the suite plays them too, one TAP line each
```

Server: `await chargerModule<typeof import('…')>('exemple')` (`src/wasm/charger.ts`; `WASM_DIR` alone if set, otherwise the loader's own directory, then `dist/wasm/`, then `rust/pkg/`). Node >= 20 as everywhere else; `rustup` must be installed, it fetches the toolchain pinned in `rust/rust-toolchain.toml`. ## Application version

`/healthz` returns `kanevas <version>`. This version comes **exclusively**
from the Docker build-arg `APP_VERSION`, never from `package.json` (which deliberately has
no version):

```bash
# without --build-arg, the version is 0.0.0-dev
docker build --build-arg APP_VERSION=0.1.0 -t kanevas:0.1.0 .
docker run --rm -p 3001:3001 kanevas:0.1.0
curl http://localhost:3001/healthz   # -> "kanevas 0.1.0"
```

An image is built only on a `v*` tag whose commit carries the « tests-complets » attestation: `attester --publier` (workstation, chain pod) sets it after a complete suite; `docker-publish.yml` runs no test, it checks this proof (without it, the tag produces no image; no build on `main` or PRs).

Each job of the workflow is bounded to 120 minutes (`timeout-minutes: 120`), so a stuck build is cut and can be re-run instead of holding the delivery for the platform's 6-hour default. A stable build (amd64 + arm64) usually takes 40 to 55 minutes; a pre-release tag (with a `-`) builds amd64 only, so it proves the workflow stays valid, not that 120 minutes suffice. A cut build is replayed from the Actions tab (« Run workflow », choosing the tag as ref, `workflow_dispatch`). A job added to the workflow must carry the same `timeout-minutes: 120`.

On a tag, CI derives that same build-arg from the pushed semver tag (`docker/metadata-action`):
pushing `v0.1.0` publishes `ghcr.io/antorfr/kanevas:0.1.0` with `APP_VERSION`
embedded as `0.1.0` — a single source of truth for the displayed version and the
published tag. Only a tag gives a reliable version: no automatic build exists outside tags.

## OIDC

`GET /api/auth/oidc/login` and `GET /api/auth/oidc/callback` reuse
Antre-du-maitre's generic mechanism (OIDC discovery, PKCE, state), stopping
at identity authentication: the callback opens the session (signed cookie,
7 days, AD-56) and creates the account on first sign-in; universe roles never
come from Authelia (AD-9). `KANEVAS_STUB=1` replaces Authelia with test account
selection (`/connexion-bouchon`, AD-55). `GET /api/auth/config` returns `{oidcEnabled}`. Without all four
`OIDC_*` variables set (see `.env.example`) — even if only some are set —
login and callback return `404`: no degraded mode. A set but
empty or invalid value (malformed URL), however, makes startup fail
(`ZodError`, `src/config/env.ts`).
